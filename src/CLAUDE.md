# src/ — architecture & code-writing conventions

Loaded automatically when working under `src/`. Extracted from the root `CLAUDE.md` to keep it out
of context for doc-only / config sessions. The route/model invariants that are easy to violate
(**Route File Organization**, **Custom Prefixed Unique Model Keys**, **Collection Document
Timestamps**) and the **Code Comments** policy stay in the root file.

## Architecture

**Binary/library split**: `src/lib.rs` re-exports `app`, `clients`, `core`, `domain`, `modules`, `workers` as a library crate. `src/main.rs` is a thin binary that wires config → Mongo → router → serve. This split exists so `src/bin/*.rs` (seed scripts) and `tests/*.rs` (integration tests) can reuse the same modules via `simplebash_pos_backend::...` — Cargo integration tests and extra `src/bin/` binaries are separate crates and cannot use `crate::` paths from `main.rs`.

**Request flow**: `main.rs` calls `Config::from_env()` (`core/config/env.rs`) → initializes database (`clients::sqlite::connect()` for SQLite or `clients::mongo::connect()` for MongoDB) → builds `AppState { config, db, document_server, reports_engine }` (defined in `app.rs`) → optionally executes `seeds::seed_all()` if `config.auto_seed` is true → `app::build_router(state)`. `app.rs` builds an `OpenApiRouter` (nesting each feature module's router under `/api/<module>`, e.g. `/api/billing`, `/api/print-jobs`), splits it into an `axum::Router` + `utoipa::openapi::OpenApi`, merges in Swagger UI, then applies `CorsLayer` (all origins allowed) and `TraceLayer`.

**Request logging** (`core/logging/`): every request is printed with no setup needed — `main.rs` calls `core::logging::init` with a default filter of `simplebash_pos_backend=info,tower_http=info,info` (overridable via `RUST_LOG`), and `app.rs`'s `TraceLayer` is explicitly configured with `DefaultMakeSpan`/`DefaultOnRequest`/`DefaultOnResponse` at `Level::INFO` — tower_http's own defaults for those three are `DEBUG`, which would stay silent under an `info`-level filter. If this layer is ever touched, keep it at `INFO` (or lower the filter instead) so request activity doesn't silently disappear. On top of that, the outermost `core::logging::request::log_requests` layer gives every request a `request_id` (the caller's `X-Request-Id` when valid, else a minted `req_…`, echoed on the response and forwarded to document-server), opens a `request` span (`request_id`/`user_id`/`device_id`) that every line inside the handler inherits, and logs `http/request` + `http/response` (status, latency, sizes, and — with `LOG_HTTP_BODIES=true` — bodies redacted by `core::logging::redact`). `AppError` logs 4xx at WARN and 5xx at ERROR. `LOG_FORMAT=json` (set only by the Tauri desktop shell) switches output to local-offset JSON lines that the shell ingests into the unified desktop activity log; `LOG_SQL` (`all`/`slow`/`off`) controls SQLite statement logging in `clients::sqlite`. In that mode `core::logging::control` also reads **stdin** for `{"cmd":"log_mode",…}` lines, so the desktop can turn logging down or off at runtime (used by its benchmark) — `LogSettings` keeps `enabled`/`http_bodies`/`sql` in atomics and a `filter_fn` layer applies them per event, so never cache those values in a local. Bodies over 4x the cap are scrubbed as text instead of parsed (`redact::body_for_log`), which keeps logging a multi-MB body O(cap). The web deployment sets none of these and keeps plain text. **Every mutating service function** wraps its body in `core::logging::domain::tracked("<module>.<event>", async move { … }).await`, which records one `category=domain` line (outcome, duration, the returned record's `key`); add the same wrap to any new create/update/delete/business-action service function. Contract for the JSON shape: `docs/logging.md` in the compose repo.

**Feature modules** (`src/modules/<name>/`): one per frontend feature. `suppliers`/`supplier_products`/`purchases` are split into three modules because the frontend itself splits them into three feature folders — see **Suppliers, supplier-products & purchases** below; `auth`/`users` split the same way — see **Auth, users & permissions** below. Every module is layered the same way: `routes.rs` (HTTP only — extractors, `#[utoipa::path]`, `pub fn router() -> OpenApiRouter<AppState>`) → `service/` (business rules: validation, orchestration, translating a missing repository result into the right `AppError`) → `repository/` (Mongo only — no `AppError::not_found`, just `Option`/`Vec`/counts straight from the driver). `mod.rs` declares `repository`/`service` as **private** submodules (`mod repository; mod service;`) so nothing outside the module tree can reach past `routes` into persistence, exposing only `pub mod routes;` (plus `pub mod model;` for `inventory`, which also has Mongo document shapes to hold). Within a module, `repository`/`service` functions are `pub(crate)` and called via fully-qualified paths (e.g. `repository::product::find_product_by_id`) rather than a `pub(super) use *` re-export — repository functions are prefixed by the entity they act on (`find_product_by_id`, `find_category_by_name`, not bare `find`) specifically so sibling files like `product.rs` and `category.rs` can each have their own `insert`/`delete`-shaped operation without name collisions if ever flattened. `reports` (`modules/reports`; domain types in `domain/reports.rs`) provides full POS reporting and financial intelligence (`GET /reports/dashboard`, `GET /reports/daily-sales`, `GET /reports/monthly-profit`, `GET /reports/outstanding`, `GET /reports/employee-commissions`, `GET /reports/inventory-valuation`, `GET /reports/top-products`). All reporting routes require auth and the `reports:view` permission (`perm::REPORTS_VIEW`, granted to Admin and Manager roles; 403 `PERMISSION_DENIED` for Staff). Supported date presets (`preset` query parameter: `today`, `yesterday`, `this_week`, `this_month`, `last_month`, `this_year`, `all_time`, `custom`) are resolved centrally by `service::dates::parse_date_range`, with custom `from`/`to` string bounds supporting both RFC3339 timestamps and calendar `YYYY-MM-DD` strings. Aggregations use Mongo `$facet`, `$group`, `$unwind`, and `$lookup` pipelines over `invoices`, `payments`, `products`, `repairs`, `print_jobs`, and `credit_notes` to compute actual figures with zero client-side calculation burden. Financial metrics account for multi-line split receipts, repair/print cost deductions, employee commission splits (`percentage` vs `fixed`), return refunds, and uncollected debtor receivables. `inventory` is built out as the reference example: `service`/`repository` are further split into `product.rs`/`stock.rs`/`category.rs`/`subcategory.rs` (full product CRUD — list/get/create/update/delete, batch delete, stock adjustment + movement history, low-stock — plus full category/subcategory management. Every route in this module except the `GET /` module-status stub requires a token: reads are gated by `CurrentUser::require_permission(INVENTORY_READ)`, product/stock writes by `INVENTORY_WRITE`, and create/rename/delete a category plus add/remove a subcategory stay behind `AdminUser` — see `core/middleware/auth.rs`) backed by a `categories` collection and a separate `subcategories` collection (both seeded via `cargo run --bin seed_providers`). **Cross-collection references always go through the referenced document's `key`, never its (renameable) name or its Mongo `_id`** — this is the general pattern for any module that owns reference data another record points to: a `ProductDocument` stores `category_key`/`subcategory_key` (immutable foreign keys, generated once and never client-supplied — see **Custom Prefixed Unique Model Keys** in the root `CLAUDE.md`), never a category/subcategory name string. This makes renaming a category (or subcategory) a pure display-label change — `service::category::update_category` never needs to cascade a rename onto `products`, since the FK it stores never changes. Deleting still guards against orphaning: `delete_category`/`remove_subcategory` block with a 409 (`CATEGORY_IN_USE`/`SUBCATEGORY_IN_USE`) while any product still references that `category_key`/`subcategory_key`; once the guard passes, `delete_category` also cascade-deletes every `SubcategoryDocument` under that category (safe because a product can only hold a `subcategory_key` whose subcategory has that same `category_key` — enforced by `service::product::ensure_valid_category` at write time). `CreateProductRequest`/`UpdateProductRequest` and the category/subcategory admin endpoints' path params are all key-based (`categoryKey`/`subcategoryKey` in JSON and URL path segments) — a client must resolve a display name to its key (e.g. via `GET /categories/valid`) before submitting a write; API *responses* additionally include the resolved display name alongside the key (e.g. `Product.category`/`.categoryKey`) so callers don't have to cross-reference `GET /categories` just to render a label. `model.rs` holds its Mongo document shapes (kept separate from `domain::inventory`'s API-facing types). See **API docs** in `src/modules/CLAUDE.md` for the required pattern when adding routes, and use `inventory` as the template for building out another module's `service`/`repository` layers.

**Reports, Analytics & Chart Engine** (`modules/reports/engine/`; domain types in `domain/reports.rs`): provides a unified, high-concurrency analytical engine (`AnalyticsEngine`, held on `AppState`) that accelerates reporting endpoints and frontend dashboard feeds:
  - **In-memory cache & tag-based invalidation** (`modules/reports/engine/cache.rs`): thread-safe cache with atomic TTLs (60s for active periods like `today`, 5 mins default, 1 hr for closed historical periods). Supports tag-based eviction (`invalidate_active()`) which purges open/active period keys without clearing closed historical months.
  - **Mutation-driven cache invalidation**: billing mutations (`complete_sale`, `void_invoice`, `record_payment`, `create_credit_note`, `void_credit_note`) trigger `state.reports_engine.invalidate_active()` to keep analytics real-time and fresh with zero stale reads.
  - **SingleFlight request coalescing** (`modules/reports/engine/singleflight.rs`): wraps Tokio `broadcast::channel` to deduplicate identical concurrent analytics queries across simultaneous callers, running only 1 Mongo aggregation run and broadcasting the result to all awaiting clients.
  - **Multi-dataset engine feed** (`modules/reports/engine/feed.rs`): `GET /api/reports/engine/feed` takes `section` (`overview`, `sales`, `profit`, `customers`, `staff`, `all`) and date presets, bundling KPIs, timeseries, payment mixes, sales patterns, category breakdowns, discounts, refunds, customer rankings, and aging charts into a single unified JSON response in parallel via `tokio::try_join!`.
  - **Rust chart vectorizer** (`modules/reports/engine/charts.rs`): precomputes cumulative revenue/profit curves, 7-day rolling moving averages, top-N categories with normalized `"Other"` buckets, and peak hour/day heatmap analysis directly in Rust in microseconds.
  - **Dedicated invalidation endpoint**: `POST /api/reports/engine/invalidate` allows explicit cache clearing behind `perm::REPORTS_VIEW`.

**SKU generation** (`modules/inventory/service/sku.rs` + `repository/sku_counter.rs`): a product's `sku` is never client-supplied — `CreateProductRequest` has no `sku` field. `service::product::create_product` validates `category_key`/`subcategory_key` (`service::product::ensure_valid_category`, which also resolves and returns the category/subcategory **names** for the keys) and generates the SKU from those resolved names by calling `service::sku::generate_sku(db, category_name, subcategory_name)`, which derives a 3-letter uppercase code per name (`service::sku::derive_code` — first 3 ASCII letters, padded with `X` if the name has fewer than 3) and appends an atomically-incremented, per-prefix sequence (e.g. `"Phone Repairs"` + `"Screens"` → `PHO-SCR-0001`, `PHO-SCR-0002`, ...). `generate_sku`/`derive_code` themselves are unaware of keys — they always operate on names, resolved by the caller first. The sequence lives in a dedicated `sku_counters` collection (`{ _id: "<prefix>", seq }`), incremented via `find_one_and_update` + `$inc` + `upsert(true)` — the standard Mongo auto-increment pattern, safe under concurrent creates without a uniqueness-retry loop. SKUs are generated once and are immutable thereafter (`update_product` never touches `sku`, even if `category_key`/`subcategory_key` changes) — apply the same "generate from a derived code + atomic counter, never let the client set it" approach to any other module that needs a human-readable, collision-free identifier.

**Suppliers, supplier-products & purchases** (`modules/suppliers`, `modules/supplier_products`, `modules/purchases`; domain types in `domain/suppliers.rs`/`domain/supplier_products.rs`/`domain/purchases.rs`): three separate modules, each mounted at its own top-level `/api/<name>` prefix (`/api/suppliers`, `/api/supplier-products`, `/api/purchases`), rather than one `suppliers` module with sub-paths — `supplier_products`/`purchases` are both queried by *either* `supplierKey` or `productKey` (a product's linked suppliers, a product's purchase history), so they're independent join/history resources, not sub-resources nested under one parent. Because each module's collection root is itself the real "list"/"create" endpoint (`GET/POST /`), none of the three has the placeholder `GET /` module-status route the other modules have — there's no unused path left for one. All three follow the same `routes.rs` → `service/` → `repository/` layering as `inventory`, with `model`/`repository` private (`suppliers::model` stays `pub` like `inventory::model`, for direct fixture seeding in tests; `supplier_products`/`purchases` don't need that, so their `model` stays private). Every route across all three — reads included — requires `AdminUser`, not just `CurrentUser`: supplier identity/pricing and purchase history are treated as business-sensitive, so even `GET /suppliers`/`GET /purchases` are behind `security(("bearerAuth" = []))` plus the `role == Role::Admin` check, not merely "any authenticated caller." (This is a deliberate departure from the read-permission/write-permission split `inventory` and `customers` use — see **Auth, users & permissions** below for why "admin" specifically, not a permission.)
  - **Cross-module access**: `supplier_products`/`purchases` both need to validate and enrich against `inventory`'s products and `suppliers`' suppliers, and `inventory::service::product::delete_product`/`delete_products` needs to cascade into `supplier_products`. Since a module's `repository` is always private (only `service` is `pub`), all of this goes through `pub(crate)` functions on the *other* module's `service`, never its `repository` — e.g. `inventory::service::product::get_product_by_key`/`get_products_by_keys` (the latter added specifically for `purchases::service::purchase::list_purchases`'s batch enrichment), `suppliers::service::get_supplier_by_key`/`get_suppliers_by_keys`, `supplier_products::service::link::delete_links_for_supplier`/`delete_links_for_product`. Apply this same "reach the other module through its `service`, add a `pub(crate)` fn there if the one you need doesn't exist yet" approach for any future cross-module dependency — never make a `repository` module `pub` to work around it. This is also why `list_purchases`' supplier/product batch enrichment stays as two `get_*_by_keys` calls plus an in-memory `HashMap` zip instead of a `$lookup` — see **MongoDB Aggregation Pipelines** below for where pipelines are and aren't the right tool.
  - **Referential integrity without fallbacks**: `supplierKey`/`productKey` (and `supplier`/`product` on a link or purchase) follow the same key-based-FK rule as `category_key`/`subcategory_key` (see **Custom Prefixed Unique Model Keys** in the root `CLAUDE.md`) — `upsert_link`/`replace_links_for_supplier`/`record_purchase` all validate both keys resolve to a real document *before* writing (404 if not), rather than trusting client input. Deleting a supplier is blocked with 409 `SUPPLIER_HAS_PURCHASES` while any purchase still references it (`suppliers::service::delete_supplier`, mirroring `CATEGORY_IN_USE`) — but only cascades a delete of its `supplier_products` links, since those are pure linking metadata, not audit history. Products stay unconditionally deletable (matching `delete_product`'s existing behavior); deleting one cascades its `supplier_products` links the same way. A `Purchase`'s embedded `supplier`/`product` enrichment is resolved live at read time and reuses the existing `resolve_display_names`-style graceful-degradation pattern — `Option<SupplierSummary>`/`Option<ProductSummary>`, omitted (never a fabricated placeholder) if the reference no longer resolves — rather than snapshotting denormalized data onto the purchase or soft-deleting the supplier/product.
  - **Stock intake**: `purchases::service::purchase::record_purchase` brings its units in as a new stock batch at the purchase's `unit_cost_cents` and `selling_price_cents` (see **Stock batches** below), through `inventory::service::stock_batch::create_batch`. Any module that moves stock goes through `inventory::service::stock::apply_stock_delta` (or `stock_batch::move_allocations` for a set of batches) with its own `StockMovementType`, never by writing `stock_quantity`/`remaining_quantity`/`stock_movements` directly.

**Stock batches** (`stock_batches`, prefix `stb_`; `modules/inventory/{model,repository/stock_batch,service/stock_batch}.rs`): a product has no price of its own. Every unit belongs to one batch (one delivery) with its own `unit_cost_cents`, `selling_price_cents` and `remaining_quantity`. Batches come from purchases, product-create `openingStock`/`suppliers[]`, import rows and positive manual adjustments (`BatchSource`). `remaining_quantity` is a **derived** column exactly like `products.stock_quantity`: the sum of the `stock_movements` carrying its `batch_key`, moved only together with a movement in `apply_stock_delta` (batch first, guarded `remaining + delta >= 0`, then the product total), recomputed by sync (`derived_sqlite`/`derived_mongo::recompute_batch`), never LWW. Read paths fill `Product.price_tiers` (one per selling price in stock, cheapest first; cost range Admin-only) via `stock_batch::attach_price_tiers` — call it on every new product read path. A sale line names its tier (`sellingPriceCents`); `plan_tier_allocation` takes that price's batches oldest first and the line stores `batch_allocations` + weighted `unit_cost_cents`; voids/returns put units back into those same batches (`allocations_for_return`, newest first). Two lines of one product at different prices are disambiguated for returns by `credit_notes::LineHint` (price on a new return, batch keys in a stored one). Pre-batch data is migrated once: SQLite in `clients::sqlite::migrate_to_stock_batches` (startup), Mongo with `cargo run --bin migrate_stock_batches` (run it with `-- --dry-run` first: read-only, per-shop counts of what would change plus warnings for zero-priced products and old lines with no cost), old backups in `backup::service::upgrade_pre_batch_backup` — all give each product the deterministic opening batch `stb_open_<productKey>` so desktop and cloud migrate to identical rows. Tests: `tests/stock_batches_test.rs` (SQLite + Atlas).

**Auth, users & permissions** (`modules/auth`, `modules/users`; domain types in `domain/auth.rs`/`domain/users.rs`): split into two modules along the same "one module per frontend concern" line as `suppliers`/`supplier_products`/`purchases` — `users` owns the `users` collection, `UserDocument`, and all account CRUD/role management (admin-provisioned only; there is deliberately no public self-registration endpoint), while `auth` owns only its own `login_sessions` audit-log collection and exists to issue and describe JWTs (`POST /auth/login`, `GET /auth/me`, `GET /auth/sessions`). `auth` never touches the `users` collection directly — it reaches account data exclusively through `users::service::verify_credentials`/`get_user` (`pub`, not `pub(crate)`, specifically so `auth` — a sibling module — and `src/bin/seed_admin.rs` — a separate binary crate — can both reach it), the same "reach the other module through its `service`, never its `repository`" rule `supplier_products`/`purchases` already follow for `suppliers`/`inventory`. Three fixed roles (`domain::users::Role::{Admin,Manager,Staff}`) each map to a hardcoded default permission set (`core::constants::roles::default_permissions`) built from flat string constants in `core::constants::permissions` (`"module:action"`, e.g. `"users:manage"`, `"sessions:view"`) — adding a new permission for a future module is two edits: a new constant in `permissions.rs`, then slotting it into the relevant role's slice in `roles.rs`. `suppliers`/`supplier_products`/`purchases` deliberately have no corresponding permission constants — they're gated by `AdminUser` directly (see above), since only Admin may touch them at all; a permission would imply finer-grained delegation that doesn't exist there. `inventory` is the reference example of the permission pattern instead: `INVENTORY_READ` (held by all three roles) gates every read, `INVENTORY_WRITE` (Admin and Manager only) gates every product/stock mutation, so a Staff token can browse the catalog and its audit trail but never change either. Permissions are never persisted per-user (no per-account overrides) — they're derived fresh from `role` at every login and embedded in the JWT's `permissions` claim, so route-level checks never need a database round trip; a role change only takes effect on that user's next login, since there is no revocation/blacklist infra to force-refresh a live token.

**User-management hierarchy**: `modules/users`' own endpoints (`GET/POST /users`, `GET/PATCH/DELETE /users/{id}`) are gated by `CurrentUser::require_any_permission(&[USERS_MANAGE, USERS_MANAGE_STAFF])`, then further scoped in `service` by the caller's role via `manageable_roles(caller_role) -> &[Role]` (private to `modules::users::service`): an Admin (`USERS_MANAGE`) may create/view/edit/delete Manager and Staff accounts; a Manager (`USERS_MANAGE_STAFF`) may do the same to Staff accounts only; Staff has neither permission and can't reach these endpoints at all. Critically, **an Admin account is never manageable through this API by anyone — not even by another Admin** — `Role::Admin` never appears in any caller's `manageable_roles`, so `GET/PATCH/DELETE /users/{id}` against an Admin-role id 404s (`USER_NOT_FOUND`) exactly as if that id didn't exist, and `POST /users`/`PATCH /users/{id}` reject `role: "admin"` with 403 `PERMISSION_DENIED` for every caller, Admin included. This is a single-shop POS deployment that only ever has one Admin: `service::create_user` (the raw, unrestricted function `src/bin/seed_admin.rs` calls directly, bypassing the HTTP-reachable `create_user_for_caller` wrapper that enforces the scoping above) additionally refuses to insert a second `role: Admin` document at all (409 `ADMIN_ALREADY_EXISTS`), so even re-running `seed_admin` with a different email can't create a second one. One consequence of no role ever managing its own role: there is no dedicated "can't delete your own account" guard — it's unreachable by construction (an Admin can't target Admin, a Manager can't target Manager), so don't reintroduce one unless the hierarchy itself changes. `POST /api/auth/login` verifies username/password (login identity = shop code + username; the lookup is tenant-scoped) via `argon2` (`users::service::hash_password`/`verify_password`, Argon2id via the `password-hash` crate's `PasswordHasher`/`PasswordVerifier`) and, on success, returns a single access JWT (`jsonwebtoken`, HS256) — no refresh token, `JWT_EXPIRY_HOURS` (a required env var, in `core/config/env.rs`) controls how long it stays valid, and the client just re-authenticates via login once it expires. `GET /api/auth/me` re-reads the account from Mongo (rather than only decoding the token) specifically so a deactivated (`isActive: false`) account is caught on its next `/me` call even though its still-valid token can't otherwise be revoked. `core::middleware::auth::CurrentUser` additionally carries `permissions: Vec<String>` decoded straight from the JWT; `CurrentUser::require_permission(&self, permission: &str) -> AppResult<()>` (403 `PERMISSION_DENIED` if absent) is the pattern for gating a route by permission instead of by role — called as the first line of the handler body rather than via a new extractor type, since Axum's `FromRequestParts` can't take a runtime constructor argument without unstable const generics over `&'static str`; `AdminUser` (unchanged in shape, now compares against `Role::Admin` instead of the literal string `"admin"`) remains the pattern for "must literally be Admin" gates like `inventory`'s existing category/subcategory management — it is deliberately *not* migrated to `require_permission` here, since that would be a pure refactor with no behavior change. Every successful login is also recorded in `auth`'s own `login_sessions` collection (`modules::auth::model::LoginSessionDocument`, listed via the permission-gated `GET /api/auth/sessions`) — unlike every other cross-module reference in this codebase, its `name_at_login`/`username_at_login`/`role_at_login` fields are a **snapshot at the moment of login**, not a live join against the current account (contrast with `Purchase`'s live-resolved `supplier`/`product` enrichment): an audit trail should keep reading the way it did when the login happened even if the account is later renamed or its role changes. Bootstrap default seed data with `cargo run --bin seed_all` or seed the first Admin account with `cargo run --bin seed_admin` (username `admin` / `admin@1234`, create-if-missing, with optional `SEED_ADMIN_*` env overrides — never resets an existing account's password on re-run) since admin-provisioned-only registration otherwise has no way to create the very first user.

**Billing** (`modules/billing`; domain types in `domain/billing.rs`): owns the `invoices`/`payments` collections and everything downstream of a completed sale — `POST /billing/sales` (complete a sale), `GET /billing/invoices`/`GET /billing/invoices/{id}`, `POST /billing/invoices/{id}/cancel`, `POST/GET /billing/invoices/{id}/payments` (record/list installments against a credit sale), and `GET /billing/invoices/{id}/documents/{documentType}` (renders the invoice/receipt via an external document-server's Typst templates — see `service/print_payload.rs`). There is no tax concept anywhere in this module.

**Quotations** (`modules/quotations`; domain types in `domain/quotations.rs`): priced offers for a customer, independent of any sale — `POST/GET /quotations`, `GET /quotations/{id}`, `POST /quotations/{id}/cancel`, `GET /quotations/{id}/document` (PDF). Every route requires `quotations:manage` (`perm::QUOTATIONS_MANAGE`, held by **Admin and Manager only**, checked first in each handler), so a Staff token is refused server-side. A quotation never touches stock, payments, invoices or reports. All totals are recomputed in `service::create_quotation` (via `core::calculations`); a `productKey` line takes name/SKU/price from the catalog, the customer record wins over typed values, and the shop profile is read from `settings` and frozen on the row (kept out of API responses; it can carry a base64 logo). The number is `QUO-0001` from the `quotation` sequence (one running counter — no year). Status is `active|cancelled`; "expired" is derived from `valid_until` at read time. Content is immutable after create, which is what makes caching the PDF by quotation key safe — the cancelled state has its own cache key because the PDF is stamped. Synced via `SYNC_RESOURCES` (`ResourceSpec::lifecycle`, order 135) with `Lifecycle` merge (body immutable, status only moves forward to `cancelled`, never undone). Number blocks (`quotation`, block size 20) reserved by desktop instances prevent offline collision. Its document kind `quotation` (`documents/kinds.rs`) and payload builder `print_payload::build_quotation_data` follow the document-server contract above. Tests: `tests/quotations_test.rs`, `tests/sync_device_test.rs`, `tests/sync_cloud_test.rs`, and `tests/sync_convergence_test.rs`.

**Labels** (`modules/labels`; domain types in `domain/labels.rs`): QR/barcode sticker printing for inventory. A **label design** (`label_templates` / SQLite `label_templates`, key `ltpl_…`, per shop, **not** synced like `shop_profiles`) is a size plus ≤30 absolutely placed elements (`text` | `barcode` | `qr` | `line`, tagged enum `LabelElement`, every field required); three ready-made starters live in code (`service/starters.rs`, keys `starter_*`, read-only: 409 `LABEL_TEMPLATE_BUILT_IN`). Names are unique per shop (starters included, case-insensitive: 409 `LABEL_TEMPLATE_NAME_TAKEN`). Routes (listing designs needs `inventory:read`; everything else — designs, preview, render, print jobs, coverage — needs `inventory:write`, so **printing is Admin and Manager only**; no new permission so no re-login): `GET/POST /labels/templates`, `PUT/DELETE /labels/templates/{key}`, `POST /labels/render` (`{templateKey, items[]}` → PDF, one page per sticker; the print window's **preview**, never recorded) and `POST /labels/preview` (an unsaved design + sample → PDF). **Print history** (`service/jobs.rs`, `label_print_jobs` / SQLite `label_print_jobs`, key `lpj_…`, per shop, **not** synced — desktop and web keep separate histories): `POST /labels/jobs` renders exactly like render, then records the job (design/person/product names snapshotted, `action` print|download, `method` system|direct, printer, dpi, items with serials, total) and answers the PDF with the key in the `X-Label-Job-Key` header (exposed by the CORS layer in `app.rs`); a print starts `rendered` and the computer reports `sent`/`failed` once via `PATCH /labels/jobs/{key}` (409 `LABEL_JOB_ALREADY_REPORTED`), a download is `sent` at once. `GET /labels/jobs` (paged, `from`/`to`/`productKey`/`action`), `GET /labels/jobs/{key}`. `GET /labels/coverage` gives every product (full `Product`) its state: `never` (in stock, never labelled), `needed` (units from batches **entered** — `created_at`, not the backdatable `received_at` — after the last non-failed label still in stock, via `inventory::service::stock_batch::in_stock_units`), `labelled`, or `null` (never labelled, nothing in stock), plus counts; it scans the catalogue in memory (a marked shortcut). An item is a product (`productKey`, `copies`, `priceCents` which must be one of the product's **current price tiers**, required only when the design has a price element) or a serial (`serialNumber`, in-stock only, printed at its own batch's price); name, SKU, category, barcode and price are always resolved server-side. Limits: 200 items, 500 copies per item, 500 stickers per print. Barcodes are always Code128 and QR codes encode the same `code`; `service/validate.rs` refuses a barcode/QR that would print thinner than 0.25 mm per module (`LABEL_BARCODE_TOO_NARROW` / `LABEL_QR_TOO_SMALL`; its Code128/QR module estimators were measured against Zint/zebra output and padded). Rendering goes through `documents::service::render_uncached` with the kind `product-label` (its default template, "Product Sticker Label"); `service/payload.rs::build_label_data` builds the payload and its `schema_drift_tests` validate every starter against the real `document-server/templates/labels/*.schema.json` (they **panic**, not skip, when that checkout is missing). Two inventory endpoints came with it: `POST /inventory/products/{id}/barcode` gives a barcode-less product a generated one (409 `PRODUCT_HAS_BARCODE` if it has one; bumps the version so it syncs) and `GET /inventory/serials/by-number/{serialNumber}` resolves a scanned serial to its in-stock unit, product and batch price (404 `SERIAL_NOT_FOUND`, 409 `SERIAL_ALREADY_SOLD`; the billing till uses it). Tests: `tests/labels_test.rs` (the design/print scenario and the print-jobs/coverage scenario each on SQLite and on a throwaway Atlas DB, permissions, per-tenant isolation of designs and history), unit tests in `service/jobs.rs`, unit tests in `service/{validate,starters,payload}.rs`; the mock document-server (`tests/common`) publishes a label template and echoes the request JSON into its fake PDF text.

**Cash movements, cash categories & payees** (`modules/sessions` movements, `modules/cash_categories`, `modules/payees`; domain types in `domain/sessions.rs` and `domain/cash_categories.rs`): every drawer cash event is a typed, append-only `cash_movements` row. `CashMovementType` has eight values (`petty_expense`, `rent_and_bills`, `staff_payment`, `supplier_payment`, `owner_withdrawal`, `add_cash`, `cash_drop`, `no_sale`); `direction()` (`out`/`in`/`neutral`) is derived from it and stored on the row. There is no free-text reason: a row points at a **category** by `category_key` (plus an optional one-off `custom_label`, only allowed on the type's "Other" category), and carries `payee_key`/`payee_name`, `period_start`/`period_end`, `reference_no` and `note`. Rules live in one place, `sessions::service::movement::record_movement`: the shift (when `session_key` is given; omitted only for cash taken out between shifts) must be open on that terminal; amount > 0 except `no_sale` (exactly 0); the category must belong to the type and be visible; each type asks for its own fields and **refuses the others** (`forbid`) instead of silently dropping them; a saved payee is resolved through its owning module (`payees::service::resolve_payee`: `sup_` suppliers, `emp_` staff, `pye_` stored payees), never trusted from the client; a name typed on a petty expense is saved as an `other` payee; a manager/owner PIN is required for owner withdrawals, staff payments and any amount above the category's `requires_approval_over_cents` (the old hard-coded Rs. 500 admin threshold is gone). `rent_and_bills`, `staff_payment` and `supplier_payment` also need `cash_movements:create:managed` (checked in the route via `requires_managed_permission`). Session totals keep their four buckets (`add_cash` -> pay-in, petty/rent/staff/supplier -> pay-out, owner, drop); `calculate_expected_cash` is unchanged.
  - **Drawer safety**: a payout (any outgoing kind, or a cash drop) bigger than the cash the drawer holds is refused with 409 `DRAWER_CASH_EXCEEDED` unless a manager or owner `managerPin` **and** an `overrideReason` are sent; both are stored (`approved_by_*`, `approval_reason`). The cash is the open shift's `calculate_expected_cash()`, or between shifts the drawer's own running balance (`drawer_state`). **Reversal** (`POST /sessions/movements/{key}/reverse`, `reverse_movement`) never edits or deletes: it inserts the opposite movement (same type and amount, `direction` flipped, `reverses_key` = the original, note "Reversal of CSH-…"), takes the amount back out of the shift's bucket and the drawer, and the original gains `reversedByKey` at read time (`find_reversals_of`, never stored on the original). The reversal's key is **derived from the original's** (`<key>_rev`), so a second reversal is 409 `MOVEMENT_ALREADY_REVERSED` and two devices undoing the same entry offline are one row; a reversal or a no-sale open is 400 `MOVEMENT_NOT_REVERSIBLE`; the shift must still be open. The person who recorded a movement can undo it for `UNDO_WINDOW_SECONDS` (120, a fixed policy constant for now; it moves to the shop settings screen later), shown to clients as `undoUntil`; after that, or for someone else's movement, only `cash_movements:reverse` (Manager, Admin) can, and a reason is required. A reversed drawer payment and its reversal drop out of the expense list. The SQLite columns `approval_reason`/`reverses_key` are added by `migrate_schema`; Mongo needs nothing.
  - **Categories are data** (`cash_categories`, key `ccat_<type>_<12 hex>`, prefix `CASH_CATEGORY`): per movement type, with `report_group` (inherited from the type, only a manager may choose), `review_status` (a cashier-made category is `needs_review`, shown at once), `pinned`, `sort_order`, `active`, `requires_receipt`, `requires_approval_over_cents`. **The key is derived from the type and the normalized name** (`domain::cash_categories::category_key`, lowercase with all whitespace removed, SHA-256), not random, so the same name made on two offline devices, or seeded on a desktop and in the cloud, is one row that sync merges; there is deliberately no unique index on the name (sync apply would reject the second device's row). The service refuses a name already used by a visible or hidden category (409 `CASH_CATEGORY_NAME_TAKEN` / `CASH_CATEGORY_HIDDEN`) and a name whose derived key belongs to a since-renamed category. Hiding never deletes; **merging redirects instead of rewriting**: the source gets `merged_into_key` and `active=false`, movements keep their key (they are append-only), and readers follow the redirect (`display_names`, `keys_including_merged` for the category filter, `usage_count` sums merged sources). `usage_count` is counted from the movements at read time, not stored, so it never needs a derived-column recompute in sync. The built-in "Other" of a type cannot be renamed, hidden or merged (one-off labels and migrated rows are filed under it); built-in categories cannot be merged away.
  - **Seeding is required reference data, not demo data**: `seeds::cash_categories::SYSTEM_CATEGORIES` is ensured (idempotent, never overwrites a shop's edits) by `main` on every start for single-shop deployments, by `tenants::service::provision_shop` for each new cloud shop, by `seed_all`, and by the Mongo migration for existing shops. Test harnesses (`spawn_mongo_app`, `spawn_app_sqlite`) call it too.
  - **Payee directory** (`payees`): suppliers and active staff are **not copied**; `GET /payees` lists them live from their own modules next to the stored `vendor`/`other` rows (key `pye_<type>_<12 hex>`, derived like categories), ranked by how many movements name them.
  - **One-time migration of old rows**: SQLite in `clients::sqlite::migrate_cash_movements` (first pass of `migrate_schema`, rebuilds the table, drops sync triggers first so it is not uploaded), Mongo with `cargo run --bin migrate_cash_movements [-- --dry-run]` (`cash_categories::migration`, also seeds every shop's categories). Both map the old types to the new ones, `reason` -> `note`, the old payee text -> `payee_name`, and file the row under the type's "Other" (cash drops under "To safe") with deterministic keys. **Run the Mongo migration before deploying this backend to an environment with existing data**, and raise `cloud_store::MIN_DESKTOP_APP_VERSION` to the desktop release that carries this shape (not yet done: it needs the release number).
  - Tests: `tests/cash_categories_test.rs` (the whole scenario on SQLite and on a throwaway Atlas DB, both migrations, seed idempotency), `tests/sessions_test.rs`, the provisioning check in `tests/tenant_provision_test.rs`. Postman: *Cash Categories*, *Cash Movements*, *Payees* folders.

**Expenses** (`modules/expenses`; domain types in `domain/expenses.rs`): the ledger of record for every business cost, whichever account it moved through. **A cost paid from the drawer is entered once, as a cash movement, and is *read* into the expense list, never copied**: `service::all_rows` merges `expenses` with the drawer movements of the four outgoing kinds (`petty_expense`, `rent_and_bills`, `staff_payment`, `supplier_payment`; owner drawings and cash drops are not costs) whose category's `report_group` is `operating_expense`, `purchases` or `payroll` (a loan instalment, group `liabilities`, is left out). That keeps a drawer payment from ever being counted twice and means a later reversal only has to touch the movement. Costs paid any other way are entered here: `POST /expenses` takes `paidFrom` `bank` | `card` | `online` (paid in full on its date, one payment row) or `unpaid` (a bill, optional `dueDate`); `drawer` is refused (400) because that is a cash movement. `POST /expenses/{key}/payments` pays a bill in parts from `bank`/`card`/`online`, never more than the balance (409 `EXPENSE_OVERPAID`). `expenses` and `expense_payments` are both `AppendOnly` sync resources (`expense_number` `EXP-000001` from the `expense` sequence, with sync number blocks like other documents); **what has been paid, the balance, the status (`unpaid`/`part_paid`/`paid`) and `isOverdue` (a due date before today, UTC, and not paid in full) are worked out from the payments at read time, never stored**, so there is no derived column to recompute in sync. The list is built in memory from the whole ledger plus the drawer payments of the date range (marked `shortcut:` in `service.rs`; upgrade to a paged query for very large shops); dates are UTC like `today_utc_range`. Permissions: `expenses:view` and `expenses:manage`, Admin and Manager only (a cashier sees the drawer's own movements, not the shop's costs). A typed payee name is saved to the payee list (`payees::ensure_other_payee`). Tests: `tests/expenses_test.rs` (SQLite and Atlas). Postman: *Expenses* folder.

**Regular bills** (`modules/recurring_expenses`; domain types in `domain/recurring_expenses.rs`): the monthly bills a shop pays (rent, electricity...), with what each is expected to cost, when it falls due and where it is usually paid from. A template is `recurring_expenses` (`Lww` sync resource, key `rexp_<12 hex>` **derived from the category and payee** like categories, so one bill per category and payee and the same bill made on two devices is one row; 409 `RECURRING_EXPENSE_EXISTS`). Create/update take `amountCents`, `dueDay` (1-31; a shorter month uses its last day), `remindDaysBefore` (0-30), `paidFrom` (`drawer`/`bank`/`card`/`online`, never `unpaid`) and a note; category and payee cannot change, a bill is stopped with `active:false` (the history stays). The category must count as a cost (`category_for_expense`), and **rent and bills paid from the drawer must name a payee** (`check_payee`: the cash form always asks who, and the "already paid" check is per payee); on update that rule is checked only when `paidFrom` changes, so a bill can always be stopped. **Nothing about a month is stored**: `GET /recurring-expenses` works out, for each template, the earliest of last month and this month that is not paid in full (else this month), from the drawer movements and ledger expenses that name the same category and payee (`expenses::service::period_payments`: a drawer payment counts for its `period_start` month, a ledger expense for its date; reversed payments drop out), with `status` `upcoming`/`due` (due today or inside the reminder window)/`overdue`/`paid`, `daysUntilDue`, `paidCents`, `balanceCents`, and the payments; most urgent first. A bill added this month owes nothing for last month. `GET /recurring-expenses/period-status?categoryKey&payeeKey&period=YYYY-MM` is what the cash form calls for its warning. **Duplicate guard**: `record_movement` refuses a `rent_and_bills` movement for a month that is already paid (the bill paid in full, or anything recorded when there is no bill) with 409 `PERIOD_ALREADY_PAID` unless the request sets `confirmDuplicate`. Permissions reuse `expenses:view` (reads) and `expenses:manage` (writes). Tests: `tests/recurring_expenses_test.rs` (SQLite and Atlas) plus unit tests in `service.rs` for the due logic. Postman: *Regular Bills* folder.

**Income** (`modules/incomes`; domain types in `domain/incomes.rs`): the ledger of money received that is **not a sale** (scrap, commission, supplier refunds, interest, sub-let rent); sales stay derived from invoices (net of credit notes) and are never entered. It mirrors Expenses: **cash put into the drawer is entered once, as an `add_cash` movement, and is *read* into the income list, never copied** (`service::all_rows` merges `incomes` with `sessions::service::income_movements`, keeping only movements whose category's `report_group` is the new `other_income`; a float, owner capital or loan received stays out, and a reversed movement and its reversal cancel out). Money received into the bank, a card or online is entered with `POST /incomes` (`receivedInto` `bank` | `card` | `online`; `drawer` is refused with 400 because that is a cash movement), in full on its date, no receivables. Income categories are ordinary add-cash `cash_categories` with `report_group` `other_income` (shipped: Scrap and waste sale, Commission received, Supplier refund, Interest received, Rental income, Other income; `ensure_system_categories` adds them to existing shops at startup); `category_for_income` accepts only those, and `GET /cash-categories?forIncome=true` lists them (`forExpenses=true` lists costs). A typed payer is saved to the payee list (`payees::ensure_other_payee`), also for a drawer add-cash. `incomes` is an `AppendOnly` sync resource (`income_number` `INC-000001` from the `income` sequence; order 154); like expenses it is immutable and has no stored derived column. Permissions `income:view` and `income:manage`, Admin and Manager only. The list is built in memory (marked `shortcut:` in `service.rs`). Dates are UTC like expenses. Tests: `tests/incomes_test.rs` (SQLite and Atlas). Postman: *Income* folder.

**Accounts** (`modules/accounts`; domain types in `domain/accounts.rs`): where the shop's money is. `GET /accounts` returns four accounts, `drawer`, `bank`, `card`, `online`; **no balance is ever stored**. The drawer is the sum of every terminal's `drawer_state` running balance (`sessions::service::drawer_cash_total`). The other three start from an opening balance the owner sets once (`PUT /accounts/{kind}/opening`, `account_openings`, a `Lww` sync resource with the fixed key `aopen_<kind>` so the same account set up on two devices is one row; date today or earlier; the drawer is refused with 400) and, until then, come back with **no** `balanceCents`/`activity` (absent, not zero). After that `service::activity_since` works the balance out from activity on and after `asOfDate`: customer payments by method (`billing::service::payments::totals_by_method_since`: a refund is a negative payment row, voided invoices and deleted payments are left out; card and online only), ledger incomes received into that account (`incomes::service::account_receipts_since`), ledger expense payments paid from it (`expenses::service::account_payments_since`), and for the bank cash moved by `sessions::service::bank_cash_moves`: a `cash_drop` under "To bank deposit" adds, an `add_cash` under "Bank withdrawal to drawer" subtracts (matched by the seeded categories' deterministic keys, merged categories included; reversed movements cancel out). Not modelled: card or online settlement into the bank (each stays its own account), several named bank accounts, and bank transfers as a customer payment method (sales methods are only cash/card/online). Permissions `accounts:view` (Admin and Manager) and `accounts:manage` (Admin only). Tests: `tests/accounts_test.rs` (SQLite and Atlas) plus a unit test of the balance sum. Postman: *Accounts* folder.

**Imports & Batch Ingestion** (`modules/imports`; domain types in `domain/imports.rs`): provides a modular, extensible engine for batch spreadsheet data processing (`POST /api/imports`, `GET /api/imports`, `GET /api/imports/{key}`).
  - **Audit logging**: every processed import batch writes an `ImportBatchDocument` into `import_batches` with custom key prefix `imp_...`, capturing file metadata (`fileName`, `fileType`, `fileSizeBytes`, `totalRows`), success/failure counts, and detailed row errors.
  - **Modular handler dispatch**: `service::batch::process_import_batch` dispatches against the payload `target` (`inventory`, and in future `customers`, `suppliers`, etc.) and enforces caller permissions (`inventory:write` for inventory imports).
  - **Inventory import processor** (`service::handlers::inventory`): validates row fields, resolves categories/subcategories (with optional auto-creation when `autoCreateCategories: true`), mints sequential SKUs through `inventory::service::sku`, generates unique EAN-13 barcodes when `autoGenerateBarcodes: true`, creates products through `inventory::service::product::create_product`, and records opening stock movements via `inventory::service::stock::apply_stock_delta`.

**Document-server integration contract** (`clients/document_server.rs` → `modules/documents::service::get_or_render`, the only caller): the sibling `../document-server` is the single authority for document templates and their input contracts, and future projects integrate with it the same way. The rules this backend upholds:

1. **The published schema is the contract.** `DocumentServerClient` caches, per tenant, the `TemplateInfo` list (`key`, `name`, `family`, `version`, `kind`, `title`, `isDefault`, `options`, `dataSchema`, sample, …) from one `GET /api/templates` call (internal key + `X-Tenant-Key`); `render()` validates every payload against that schema (`jsonschema`) *before* sending and answers 422 `RENDER_VALIDATION_FAILED` with field-level messages — deliberately the same code/status that service itself answers with, so callers treat local pre-validation and remote rejection identically. When a `.typ`'s contract changes there, update its schema sidecar and the matching builder in `billing::service::print_payload` in the same change.
2. **Template identity.** Call sites address a *kind* of document by a stable slug (`a4-invoice` / `thermal-receipt` / `credit-note` / `quotation`; `analytics-report` and `product-label` are rendered by slug too but are not shop choices). A slug stands for the **built-in default template** of that kind (the one whose schema sets `x-default`, `DocumentServerClient::default_template`). A *design* is a **family** (a bundled template is its own family, id = its `doc_temp_…` name; a custom design is `fam_…`); each version is an immutable template `name`. Every `generated_documents` row persists the kind slug (`template_name`), the `tpl_…` key (`template_key`) and — since packages — `template_ref` (the version's name), `template_title` and `template_version` (nullable only for rows from before they existed, shown as unknown).
3. **Stored shared/static data is merged remotely.** That service deep-merges per-template blobs (`PUT /api/template-data/{name}/{key}`) under every payload, request fields winning — billing's per-invoice snapshots stay authoritative without resending genuinely static data.
4. Adding a bundled template = files in that service's `templates/`; a custom design = a package published to it (`POST /api/packages`) and granted to the shop; no restart on either side.
5. **Tenant scoping (`TENANT_MODE=multi`).** One document-server instance is shared across every tenant of the cloud deployment, so `clients::document_server`'s shared `forwarded_headers()` sends `X-Tenant-Key: <core::tenancy::current_tenant_id()>` on every call whenever a tenant is in scope — omitted entirely in single-shop mode (desktop, self-hosted), which is exactly document-server's pre-existing behaviour (`TenantKey::Single`). This is what stops two tenants' `template_data` blobs (shop profile, bank details) and `documents` history from leaking into each other on that shared instance; see that service's CLAUDE.md "Tenant scoping" section for the details.

6. **Shops choose their designs (`modules::documents::{kinds, service::templates}`, `modules::settings`).** `DocumentServerClient::list_templates()` returns, per tenant, the latest published version of every design family that tenant may use (bundled ones plus custom ones granted to it), cached for 60 s and served stale if a refresh fails. A shop stores one **family** per kind plus the **option values** it saved per family (`document_template_settings`, one `main` row per shop: `selections`, `options`; `GET/PUT /api/settings/document-templates`, write = Admin; the PUT body needs both `selections` — kind → family or `null` — and `options` — family → key → value —, validated against the design's `x-options`: toggle bool, select one of its choices, `#RRGGBB` colour, text ≤ `maxLength`; 422 `TEMPLATE_UNAVAILABLE` / `TEMPLATE_OPTIONS_INVALID`; plus `GET …/{family}/preview` rendering the design's own sample minus its `logoUrl`). The listing reports per kind `selected`, `effective` (`null` when the stored family is no longer offered) and `optionValues` (saved value, else the design's own declared default). **There is no silent fallback**: at print time `templates::resolve` picks `?template=<family>` → the shop's family → the kind's `x-default`, and a requested or stored family that is not offered is 422 `TEMPLATE_UNAVAILABLE` until the shop chooses again. A design that declares options gets the payload's `options` object (the effective values; `templates::with_options`). The `generated_documents` cache key stays the historical one (`a4-invoice`, `thermal-receipt-80mm`, `credit-note`) for the built-in default and is `<key>--<template name>` for any other design (and `--<8 hex digest of the option values>` when it has options, so changing a setting renders afresh). **Reprint choice**: every document endpoint (`GET /billing/invoices/{id}/documents/{type}`, `GET /billing/credit-notes/{id}/documents/credit-note`, `GET /quotations/{id}/document`) requires `design=original|current` (400 when missing): `original` serves the newest stored PDF of that print variant whatever design made it (`documents::service::get_original`, 404 `NO_ORIGINAL_DOCUMENT`), `current` resolves and renders/caches as above. The sibling `…/design` endpoints answer `{stored: {templateRef, title, version, createdAt}|null, current: {templateRef, title, version}, differs}` (`differs` only when the stored row recorded another template). Cloud only: `GET /api/document-packages` and `GET /api/document-packages/{name}/archive` (any shop token incl. the desktop device token) list/proxy the shop's private designs for desktops to mirror. Every template of a kind must accept that kind's standard payload; `print_payload::schema_drift_tests` validates each builder's payload against **every** public schema declaring the kind. Tests: `tests/document_templates_test.rs` (settings and options on SQLite; printing, original/current, option caching, per-tenant isolation and the console's reset on throwaway Atlas databases), `tests/document_template_cache_test.rs`, `tests/document_packages_test.rs`, the resolver unit tests in `service/templates.rs`.

**Shop provisioning (`modules/tenants`, `TENANT_MODE=multi` only).** Shops are registered by the cloud identity service (`cloud/identity-server`), which then calls `POST /api/internal/provision` (nested at `/internal` in `app.rs`) with header `X-Provision-Secret` = `PROVISION_SECRET` (`core/config/env.rs`, min 16 chars) and body `{tenantId, shopCode, name, owner?: {username, name, passwordHash}}`. It creates the tenant directory entry (`tenants::service::provision_shop` → the existing `create_tenant_with_key` logic) and, when `owner` is present, the shop's first Admin inside `with_tenant(...)` via `users::service::create_owner_admin_if_absent`; `username` must be `admin` (`roles::ADMIN_USERNAME`) and `passwordHash` is identity's Argon2id PHC string of the admin password the owner chose for this shop (both services use `argon2` 0.5.3 defaults), validated with `validate_owner_login` and stored as-is. Provisioning is a replay-safe sync: replaying refreshes the shop name and the Admin's display name (never its password hash), and identity replays it on login, `PATCH /v1/me` and `POST /v1/me/resync`. Interactive identity tokens (`scope: account`, with `email`/`name` claims and a `tid`) are accepted as Admin; `/auth/me` and `perform_setup` resolve their `acc_…` subject to the shop's Admin (`users::service::find_user_for_identity`).
  - **Guard, not a JWT**: `routes.rs::authorize()` returns **404** when not in multi mode or no secret is configured, **401** on a wrong secret (constant-time compare). The route is therefore listed in `PUBLIC_ROUTES` in `tests/authorization_test.rs`, and nginx answers 404 for `/api/internal/` from the internet — it must stay reachable only over the docker network.
  - **Idempotent and validate-first**: everything (tenant key, shop code, name, owner hash) is validated before any write; a repeat call returns 200 with `data.tenantCreated:false` (standard `ApiResponse` envelope); a shop code owned by a different tenant is `409 SHOP_CODE_ALREADY_EXISTS`, a tenant id under another code `409 TENANT_ALREADY_EXISTS`. The Admin is created only if the tenant has none.
  - Tests: `tests/tenant_provision_test.rs` (uses `spawn_app_multi_tenant_with_secret`). Postman: the *Internal* folder + `provisionSecret` variable.

**Shop suspension and usage (`modules/tenants`, operator console).** The identity service switches a shop's cloud access off and on when an operator suspends or reinstates the owner's account, by calling `PUT /api/internal/tenants/{tenant_id}/status` `{suspended, suspendedAt, reason}` (same `X-Provision-Secret` guard as provisioning; idempotent; 404 `TENANT_NOT_FOUND` for a shop that was never provisioned; 400 unless `suspendedAt` (RFC 3339) and a 1-500 character `reason` are present exactly when `suspended` is true). It sets/clears `tenants.suspended_at` (identity's own time, never re-stamped here) and `tenants.suspended_reason`.
  - **Enforcement is one place**: `core::middleware::tenant::tenant_context` (every request in multi mode) refuses a request whose token belongs to a suspended shop with `403 ACCOUNT_SUSPENDED`, before any handler, for staff, device and identity tokens alike. The error carries `details {shopName, suspendedAt, reason, retained {bills, products, customers, staff, lastBillAt}}` for the web suspended page; `retained` is computed with `tenants::usage::usage_for` (counts only) so the page can show the shop's data is still stored. `tenants::service::suspension_of` caches that whole answer for 30 s per tenant per instance (`set_suspended` drops the local entry, so this instance re-reads at once and only *other* instances lag by up to 30 s); a directory read error **fails open** with a warning, since the handler's own queries would fail too. `auth::service::login_in_scope` also refuses a shop-code login **after** the password was verified, so a stranger cannot probe which shops are suspended. Single-tenant (desktop/self-hosted) deployments are never affected.
  - **Open SSE streams are not closed**: `/api/sync/events` carries only `{seq, resource, origin}`, and every call that returns data (`pull`, `push`, `snapshot`, REST) is refused, so a stream that was already open reveals nothing; the desktop reconnects and is refused.
  - **Designs in use** (`GET /api/internal/tenants/{id}/document-selections`, `POST …/document-selections/reset` with `{families: [...]}`; same secret): the console checks which custom design families a shop has chosen before revoking one, and resets them explicitly (selection and saved option values) when the operator confirms. Nothing here prints or substitutes anything.
  - **Usage** (`GET /api/internal/tenants/{id}/usage`, `POST /api/internal/tenants/usage` for up to 100 ids; `tenants::usage`): counts and gross sales only (non-voided invoices; credit notes are not subtracted), products and customers without `deleted_at`, active users, non-revoked devices, last sync (max `sync_device_state.last_seen`) and 30 days of bills per Asia/Colombo day. Queries run inside `with_tenant` so the normal tenant filter applies; never add record content (names, line items) to this response.
  - Tests: `tests/tenant_suspension_test.rs`. Postman: *Internal* folder.

The A4 invoice is document-server's branded/modern layout and carries a `logoUrl` sourced from `shopProfileSnapshot.logoBase64` (a `data:` URI — document-server decodes it inline, uses it for that one render, and drops it).

Tests: the mock document-server in `tests/common/mod.rs` serves realistic minimal `dataSchema`s (each with a `description`) so pre-validation runs for real; `start_strict_mock_document_server()` publishes an unsatisfiable schema for the A4 Invoice and pairs with `spawn_app_with_document_server_url` to exercise the fail-fast path (`billing_test.rs`). `billing::service::print_payload`'s `schema_drift_tests` load the real sidecars from `../document-server` by matching the schema `title`.

`CreateSaleRequest` (the `POST /billing/sales` body) is grouped into sub-objects by concern rather than one flat field list — the general pattern to follow whenever a request has 3+ fields that share a concern (a bare 1-2 field pair stays flat, matching e.g. `inventory`'s `categoryKey`/`subcategoryKey`, which stays flat): `staff{cashierName}`, `customer{customerKey, customerName, customerPhone, customerAddress}` (optional — omitted entirely for a walk-in with no linked account), `items[]`, `pricingAdjustments{discountType, discountValue}` (optional — omitted means no discount), `payment{paymentMethod, isCredit, amountReceivedCents, splitPayments, cardLast4, cardRef, onlineRef, onlineNote, dueDate}`, plus `shopProfileSnapshot`/`notes`/`warrantyTermsSnapshot`/`documentSelection` staying flat top-level singles (each independent, no natural group to join). `repairs`/`print_jobs` apply the same treatment to their own `CreateRepairRequest`/`CreatePrintJobRequest`/`Update*Request` bodies: `customer{customerKey, customerName, customerPhone}` (same override-from-`customerKey` rule as billing's `customer{}`) and `assignment{assignedEmployeeId, assignedEmployeeName, splitType, splitValue}` — each module still defines its own local `customer`/`assignment` sub-struct rather than sharing one, since the fields' optionality differs slightly per module and per create-vs-update. Every other module's request DTOs were audited and left flat, since none has a comparable 3+-field grouping that isn't already atomic or already a nested array (e.g. `inventory::CreateProductRequest.suppliers[]`). The *response* types (`Invoice`, `Repair`, `PrintJob`) deliberately stay flat, unrestructured — only the request bodies are grouped, to keep the change's blast radius to what actually needed regrouping.

Every field on a sale-completion item (`CreateSaleItemRequest`) that's reachable from a key is resolved server-side, never trusted from the client — the same "reach through a key, don't trust a client-sent duplicate" rule `purchases`/`supplier_products` already apply to `supplierKey`/`productKey` (see **Suppliers, supplier-products & purchases** above): a retail item's `name`/`sku` are resolved from the product record via `productKey` and its `unitPriceCents` from the price tier it names (`sellingPriceCents`, see **Stock batches**) (`inventory::service::product::get_product_by_key`); a repair/print item's `unitPriceCents` (`estimatedCostCents + materialCostCents`), `assignedEmployeeName`, and `sourceTicketNumber` are resolved from the ticket via `sourceTicketKey` (`repairs::service::get_repair`/`print_jobs::service::get_print_job`). `name`/`unitPriceCents` are only accepted from the client as a fallback for an ad-hoc line with no key to resolve against (validation error if missing in that case). An unresolvable `productKey`/`sourceTicketKey`/`customerKey` rejects the whole `POST /billing/sales` request before any write (`service::sale::resolve_sale_items`/`complete_sale`), the same "fail before any write" treatment the customer-key lookup already used.

`subtotalCents`/`discountCents`/`totalCents`/`changeDueCents` are likewise never client-supplied — all server-computed in `service::sale::complete_sale`: `subtotalCents` is the sum of the resolved items' `totalCents` (itself `unitPriceCents * quantity - discountCents`, floored at 0); `discountCents` is computed from `pricingAdjustments` against that subtotal (`service::sale::compute_discount`) — `discountType: "fixed"` uses `discountValue` verbatim as cents, `discountType: "percentage"` computes `subtotal * value / 100` (floored), and omitting `pricingAdjustments` means no discount (persisted as `discountType: "fixed"`, `discountValue: 0.0`, so the response always has a concrete value, never an `Option`); `totalCents` is `subtotalCents - discountCents` (no tax term); `changeDueCents` (when `payment.amountReceivedCents` is given) is `amountReceivedCents - totalCents`. A split payment's legs are validated against this computed `totalCents`, not any client-supplied figure.

**`core/`** — cross-cutting infrastructure, not domain logic:
- `core/config/env.rs` — `Config::from_env()` parses all required env vars once at startup and fails fast: `DATABASE_TYPE` (`sqlite` default, or `mongodb`), `DATABASE_URL` (SQLite connection string), `JWT_SECRET`, `JWT_EXPIRY_HOURS`, `AUTO_SEED` (boolean flag to auto-run `seed_all` on startup, defaults to `true`), and `MONGODB_URI`/`MONGODB_DB_NAME` when `DATABASE_TYPE=mongodb` (`PORT` defaults to 8080, `BIND_ADDR` to `0.0.0.0` — set `127.0.0.1` for the Tauri desktop bundle).
- `core/middleware/auth.rs` — `CurrentUser` is an Axum extractor (`FromRequestParts<AppState>`) that verifies the `Authorization: Bearer <jwt>` header with `jsonwebtoken` using `Config::jwt_secret`, decoding a `role: Option<domain::users::Role>` and a `permissions: Vec<String>` claim. Add `CurrentUser` as a handler argument to require auth on a route; omit it to keep a route public. **Auth is opt-in per handler and nothing flags one that forgets it** — a handler declaring neither extractor is silently public, and it still compiles, still passes every other test, and is still documented accurately by the OpenAPI derive. That is exactly how `inventory`'s product/stock routes served the whole catalog — and accepted creates, price edits, stock adjustments and bulk deletes — with no token at all. The complete intentional-public list is `GET /api/health`, `POST /api/auth/login`, Swagger (`/docs`, `/api-docs/openapi.json`) and the module-status stubs (`GET /api/inventory`, `GET /api/billing`, `GET /api/customers`, `GET /api/reports`); it is restated in a comment in `app::build_router` and enforced route-by-route by `tests/authorization_test.rs`. Anything else must take an extractor. Call `CurrentUser::require_permission("some:permission")` as the first line of a handler body to further gate it by permission (403 `PERMISSION_DENIED` otherwise). `AdminUser` wraps `CurrentUser` and additionally requires `role == Some(Role::Admin)` (403 `ADMIN_REQUIRED` otherwise) — the pattern for "must literally be Admin" endpoints like inventory's category management; add `AdminUser` as a handler argument the same way, and mark the route `security(("bearerAuth" = []))` in its `#[utoipa::path]`. There is deliberately no tenant/org-membership middleware yet — this is a single-shop deployment for now. Note `jsonwebtoken` needs its `rust_crypto` feature enabled in `Cargo.toml` (see comment there) — without it, `encode`/`decode` panic at runtime with no crypto backend installed.
- `core/error.rs` — `AppError` (`NotFound`, `Validation`, `Unauthorized`, `Forbidden`, `Internal` — each `{ message, code: Option<String> }` — plus `Custom { status, code, message }` for anything else) implements `IntoResponse`, serializing to `core::response::ErrorResponse` (`{ success: false, message, code, statusCode }`, camelCase) with the matching HTTP status; also `From<mongodb::error::Error>` / `From<jsonwebtoken::errors::Error>`, so handlers can `?`-propagate Mongo/JWT failures directly. Use `AppResult<T>` as the handler return type. Construct via `AppError::not_found("msg")` / `AppError::not_found_with_code("msg", "SOME_CODE")` (same pattern for `validation`/`unauthorized`/`forbidden`/`internal`), or `AppError::custom(status, "CODE", "msg")` for anything outside those five. A missing `code` on the non-`Custom` variants defaults to the upper-snake-case of the variant name (e.g. `NOT_FOUND`).
- `core/response.rs` — `ApiResponse<T>` is the success envelope every handler should return: `{ success: true, data: Option<T>, message: Option<String> }` (both fields omitted from JSON when `None`), built via `ApiResponse::success(data, message)` / `::data(data)` / `::message(message)`. Its `IntoResponse` impl **always returns HTTP 200** — a handler returning `Json<ApiResponse<T>>` directly (as opposed to `AppResult<Json<ApiResponse<T>>>` returning `Err(AppError::...)`) cannot produce a non-2xx status; failure cases must go through `AppError`, not `ApiResponse`. Also defines `ErrorResponse`, the JSON shape `AppError::into_response` produces (see above) — don't construct `ErrorResponse` directly outside `core/error.rs`.
- `core/constants/` — central source of truth for constants across the backend: `modules.rs` (feature module names), `codes.rs` (standardized error and status codes), `http_status.rs` (re-exported HTTP status codes), `prefixes.rs` (model key prefix constants like `PRODUCT`, `CATEGORY`, `SUBCATEGORY`, `STOCK_MOVEMENT`, `API_KEY`, `SUPPLIER`, `SUPPLIER_PRODUCT`, `PURCHASE`, `USER`, `LOGIN_SESSION`), `permissions.rs` (flat `"module:action"` permission strings), and `roles.rs` (`default_permissions(Role) -> &[&str]`, the hardcoded role→permission-set table — see **Auth, users & permissions** above).
- `core/utils.rs` — reusable cross-cutting helpers for route handlers (`module_status_response`, `parse_object_id`, `regex_escape`, `build_bson_regex`, `calculate_pagination`).
- `core/openapi.rs` — `ApiDoc` (`#[derive(utoipa::OpenApi)]`) holds only top-level metadata (title/description/version, tags, the `bearerAuth` security scheme); actual paths are collected from the modules at router-build time, not listed here.

**`domain/`** — pure business types shared across modules (no I/O, no Axum/Mongo types beyond `serde`/`utoipa` derives). Currently holds `HealthResponse`/`ModuleStatusResponse`, the inner `data` payloads that route handlers wrap in `core::response::ApiResponse<T>` before returning (e.g. `Json<ApiResponse<ModuleStatusResponse>>`, not the raw type) — populate further as modules grow instead of putting business logic directly in `routes.rs`.

**`clients/`** — persistence abstraction:
- `clients/db.rs` — `Db` enum holding either `Sqlite(SqlitePool)` or `Mongo(Database)`, providing a unified database access handle throughout all repository implementations.
- `clients/sqlite.rs` — `connect(database_url)` builds the SQLite pool (WAL mode, foreign keys enforced, 5s busy timeout) and runs schema creation from `sqlite_schema.sql`.
- `clients/mongo.rs` — `connect(uri, db_name)` builds the `mongodb::Client`, pings the target database, and returns a `Database` handle. `ClientOptions::parse` is explicitly given `ResolverConfig::cloudflare()` rather than the OS default. Modules access `AppState.db` rather than reconnecting.

**`workers/`** — placeholder for background jobs (e.g. scheduled reports, print queue processing); empty so far.

**`src/bin/`** — standalone binaries sharing the lib's config/Mongo plumbing, run via `cargo run --bin <name>`, not part of the HTTP server.

## MongoDB Aggregation Pipelines

Use an aggregation pipeline wherever the driver supports one and it collapses multiple round trips
(or an unsafe read-modify-write) into one — but a pipeline is a read/transform tool, not a
universal replacement for CRUD. Apply it by operation type:

- **Reads** — any `find`/`find_one` with a non-trivial shape (joins, grouping, counts, pagination
  computed server-side) should become `aggregate([...])`. A single `$match` stage can express any
  plain filter, so there's no reads-only case a pipeline can't cover.
- **Updates** — MongoDB 4.2+ accepts an *array of aggregation stages* in place of an
  update-operator document for `updateOne`/`find_one_and_update`, letting the new value be
  computed from the document's current fields server-side in one atomic round trip. Use this
  whenever a plain `$set` isn't enough because the new value depends on the old one (an increment,
  a computed field) — see `repository::product::adjust_product_stock_pipeline`
  (`modules/inventory/repository/product.rs`): `find_one_and_update` with a pipeline `$set`
  computing `{ "$add": ["$stock_quantity", delta] }`, with the negative-stock guard folded
  straight into the query filter (`"stock_quantity": { "$gte": -delta }` when `delta < 0`) so the
  check and the write are one atomic operation instead of a read-then-write race.
- **Inserts and deletes** — stay as plain `insert_one`/`insert_many`/`delete_one`/`delete_many`
  regardless; there is no aggregation-pipeline form of either, so there's nothing to gain.

Within those rules, only reach for a pipeline where it's a *real* win:

- **Do** collapse a "fetch collection A, fetch collection B, group/zip in Rust with a `HashMap`"
  pattern into a single `$lookup`-based aggregate **when both collections belong to the same
  module** — e.g. `repository::product::list_products_with_display_names` (`$lookup` joining
  `products` → `categories`/`subcategories`) and
  `repository::category::list_categories_with_subcategories` (`$lookup` joining `categories` →
  `subcategories`), both in `modules/inventory/repository/`. Also reach for `$facet` when one
  endpoint needs several independent aggregates (counts, grouped-and-paginated sub-results) in one
  round trip instead of issuing them as separate queries — see
  `repository::product::aggregate_overview`, which computes the Inventory & Stock overview page's
  dashboard metrics, per-category counts, and per-subcategory paginated product pages in a single
  `$facet` pipeline (replacing what used to be a query issued once per subcategory in a loop).
  `billing::repository::aggregate_stats`, `repairs::repository::aggregate_stats` and
  `print_jobs::repository::aggregate_stats` are the same pattern applied to a plain dashboard-KPI
  endpoint (no pagination/hierarchy involved) — see **Dashboard stats endpoints** below.
- **Don't** wrap a trivial single-document `find_one` (`find_product_by_id`,
  `find_supplier_by_key`, `find_category_by_name`, etc.) in `aggregate([{ "$match": ... }])` —
  that's pipeline ceremony for something `find_one` already does in one line.
- **Don't** use `$lookup` across a module boundary. `purchases::service::purchase::list_purchases`
  and `supplier_products::service::link`'s batch enrichment against `suppliers`/`inventory` stay
  as separate `get_*_by_keys` calls into the other module's `service` plus an in-memory `HashMap`
  zip (see **Cross-module access** above) — a `$lookup` there would mean one module's `repository`
  reaching directly into another module's collection, which breaks the "reach another module
  through its `service`, never its `repository`" rule this codebase enforces everywhere. That
  boundary is what lets e.g. `inventory::service::product::get_product_by_key` apply its own
  not-found/validation logic consistently to every caller — `$lookup` would bypass it.

## Dashboard stats endpoints

A screen's top-of-page KPI strip (e.g. the frontend's Sales & Invoices History, Repair Jobs, Print
Jobs screens) is always computed server-side, never left for the frontend to derive from its Dexie
mirror — `GET /billing/invoices/stats`, `GET /repairs/stats`, `GET /print-jobs/stats` are the
precedent, alongside `GET /inventory/overview`. Each follows the same shape: a `<Module>Stats` DTO
in `domain/<module>.rs`, a `repository::aggregate_stats` `$facet` pipeline computing every branch
in one round trip, a thin `service::get_<module>_stats` wrapping it, and a `CurrentUser`-only
handler at a static `/stats` path registered in its own `routes!()` call (so it doesn't collide
with a sibling `/{id}` dynamic route).

"Today" is `core::utils::today_utc_range()` — `[start, end)` UTC-midnight bounds. There is no
per-shop timezone configured anywhere in this app, so this is deliberately UTC-based, matching how
every `created_at` is already stored; it will disagree with a browser's *local* "today" near
midnight, which is an accepted limitation, not an oversight. Reuse this helper for any future
"today's X" metric rather than reimplementing a date-boundary calculation.

Because the shared test database (`tests/common::spawn_app`) has no per-test isolation and these
endpoints aggregate a whole collection with no filter, `billing_test.rs`/`repairs_test.rs`/
`print_jobs_test.rs`'s stats tests don't assert against the shared DB at all — they open their own
throwaway database (`clients::mongo::connect` with a fresh uuid-suffixed name, kept under Atlas's
38-byte database-name cap) and call the `service::get_*_stats` function directly, bypassing
HTTP/the shared fixture entirely. Follow that pattern for any test that needs an exact,
uncontaminated aggregate — the `>=` bounds `inventory_test.rs`'s overview test uses are only
appropriate when an inequality can't hide a real bug (see that test for the contrast).

## Sample-data seeding is concurrent

`seeds::inventory::seed_inventory` seeds categories (`CATEGORY_SEED_CONCURRENCY`) and creates products (`PRODUCT_SEED_CONCURRENCY`) with `buffer_unordered`, and `system::service::seed_sample_data` runs the catalog, suppliers and customers seeders together with `try_join!`. Everything stays on the request's own task, so the tenant task-local scope still applies (never `tokio::spawn` inside a seeder). Reason: over a remote MongoDB each product costs ~10 round trips, so the old one-by-one loop made a web "demo data" setup take ~2 minutes (the browser waited at 100% with no Launch button); desktop SQLite never noticed. It is only safe because SKU numbers come from one atomic `$inc` (`repository::sku_counter::bump`, which retries the duplicate-key error two first-time creators of a prefix can hit). Keep that retry if you touch the counter.
