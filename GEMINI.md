# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

The Rust/Axum API backend for **jana2u-pos**, a point-of-sale system for a repair/retail shop (billing, repairs, print jobs, inventory, customers, reports, suppliers). Persistence is MongoDB. The sibling `../frontend` (React + Vite + Mantine) is the client this API serves, expecting endpoints under `env.apiBaseUrl` (`/api` by default).

## Commands

- `cargo build` — compile
- `cargo run` — run the server (equivalent to `cargo run --bin jana2u_pos_backend`; required explicitly if disambiguating from the seed binaries)
- `cargo test` — run all tests (`tests/scenarios_test.rs`, `tests/inventory_test.rs`, `tests/suppliers_test.rs`, `tests/auth_test.rs`, and `tests/users_test.rs` require a reachable MongoDB — see below; `tests/openapi_test.rs` and `tests/response_format_test.rs` do not)
- `cargo test --test scenarios_test health_route_returns_success_format` — run a single integration test by name
- `cargo fmt` / `cargo fmt --check` — format / verify formatting
- `cargo run --bin seed_api_key` — generate and insert a random API key into the `api_keys` collection
- `cargo run --bin seed_providers` — upserts the inventory module's default category/subcategory reference data into the `categories`/`subcategories` collections (see `default_categories` in `src/bin/seed_providers.rs`)
- `cargo run --bin seed_suppliers` — upserts a handful of sample repair/retail suppliers into the `suppliers` collection (see `sample_suppliers` in `src/bin/seed_suppliers.rs`)
- `cargo run --bin seed_customers` — upserts 20 realistic retail/repair/corporate/print customer profiles into the `customers` collection (see `sample_customers` in `src/bin/seed_customers.rs`)
- `cargo run --bin seed_admin` — create-if-missing bootstrap of the first Admin account (requires `SEED_ADMIN_EMAIL`/`SEED_ADMIN_PASSWORD`/`SEED_ADMIN_NAME` to be set — see `.env.example` — fails fast rather than falling back to a hardcoded password), since registration is admin-provisioned only — see **Auth, users & permissions** below
- `make check` (defined in the root `Makefile`) — runs `cargo fmt --check`, then `cargo clippy --all-targets --all-features -- -D warnings`, then `cargo test`, in that order, stopping at the first failure; `make ci` is currently just an alias for `make check` (same steps, intended as the CI entrypoint)

**After every change**, run the following and fix anything it reports before considering the work done:

```
make check
# (or: cargo fmt --check && cargo clippy --all-targets --all-features -- -D warnings && cargo test)
```

(`cargo fmt --check` fails on unformatted code without rewriting it; `clippy -D warnings` treats every lint as an error; `cargo check` is the fast type/borrow check; `cargo build --release` is the pre-deploy build. `rustfmt`/`clippy` components must be installed — `rustup component add rustfmt clippy` — if either command is missing.)

**Every change must be tested — this is mandatory, not just running the pipeline above.** `cargo test` in that pipeline only re-runs whatever tests already exist; it does not by itself prove a new change works. So for any change:
1. Find the test file that already covers the part of the code you're touching (see the `tests/*.rs` files below) and extend it with a case for the change.
2. If no test file covers that part yet, **create one** — follow the existing naming (`tests/<area>_test.rs`) and pick the right style: no-Mongo unit/integration style (`tests/response_format_test.rs`, `tests/openapi_test.rs`) for anything that doesn't need real data, or the full-stack style (`tests/scenarios_test.rs` via `tests/common::spawn_app()`) for anything that does.
3. Run it and confirm it passes before considering the change done.

Config is loaded from `.env` (via `dotenvy`) in every binary and integration test. Copy `.env.example` to `.env` and point `MONGODB_URI` at a running MongoDB instance before running or testing — `Config::from_env()` fails fast (process exits) on missing/invalid vars, and the Mongo client pings the server at startup, so a bad connection string is caught immediately rather than on first request.

The integration test files, each a different tradeoff between speed and realism:
- `tests/scenarios_test.rs` (+ `tests/common/mod.rs::spawn_app()`) — builds the real router against a **real** MongoDB (no mocking), using `MONGODB_TEST_DB_NAME` (defaults to `jana2u_pos_test`) instead of the dev database so it never touches dev data. Use for anything that actually reads/writes Mongo.
- `tests/inventory_test.rs` / `tests/suppliers_test.rs` / `tests/auth_test.rs` / `tests/users_test.rs` — the same `spawn_app()` real-Mongo style as `scenarios_test.rs`, just split into their own files per feature area (product/category CRUD + stock in the first; supplier CRUD, supplier-product linking, and purchase/stock-intake history — including the cross-module cascade/guard behavior — in the second; login/`me`/login-session history in the third; user CRUD/role management in the fourth). Follow this pattern (own `tests/<area>_test.rs` file, `mod common;`, `send`/`send_authed` request helpers, `common::mint_token` for hand-minted role/permission tokens) when a new module needs real-Mongo coverage.
- `tests/openapi_test.rs` — builds the real router with a `mongodb::Client` that is never pinged (still needs `MONGODB_URI` to be a syntactically valid connection string via `.env`, but no live Mongo needed). Asserts the OpenAPI spec lists every module path and Swagger UI serves. Use for anything about routing/docs wiring rather than data.
- `tests/authorization_test.rs` — same no-live-Mongo construction as `openapi_test.rs`. Walks **every** operation in the generated OpenAPI document, sends it an unauthenticated request, and asserts 401 unless the route is on its `PUBLIC_ROUTES` allowlist (health, `POST /auth/login`, and the five module-status stubs) — plus the converse, that those public routes still answer, and that a route's `security(...)` annotation matches whether it really enforces auth. This is the guard for the fact that auth is opt-in per handler: a new route registered through `routes!()` is audited the moment it exists, with no edit to this file. If it fails, the fix is almost always a missing `CurrentUser`/`AdminUser` handler argument — add to `PUBLIC_ROUTES` only when a route is genuinely meant to be open, and mirror it in `app::build_router`'s comment.
- `tests/response_format_test.rs` — no router, no Mongo at all; calls `core::response::ApiResponse`/`core::error::AppError` directly and asserts the JSON shape. Use for anything about the response/error envelope itself.

## Architecture

**Binary/library split**: `src/lib.rs` re-exports `app`, `clients`, `core`, `domain`, `modules`, `workers` as a library crate. `src/main.rs` is a thin binary that wires config → Mongo → router → serve. This split exists so `src/bin/*.rs` (seed scripts) and `tests/*.rs` (integration tests) can reuse the same modules via `jana2u_pos_backend::...` — Cargo integration tests and extra `src/bin/` binaries are separate crates and cannot use `crate::` paths from `main.rs`.

**Request flow**: `main.rs` calls `Config::from_env()` (`core/config/env.rs`) → `clients::mongo::connect()` → builds `AppState { config: Arc<Config>, db: Database }` (defined in `app.rs`) → `app::build_router(state)`. `app.rs` builds an `OpenApiRouter` (nesting each feature module's router under `/api/<module>`, e.g. `/api/billing`, `/api/print-jobs`), splits it into an `axum::Router` + `utoipa::openapi::OpenApi`, merges in Swagger UI, then applies `CorsLayer` (all origins allowed) and `TraceLayer`.

**Request logging**: every request is printed to the terminal (method, URI, status, latency) with no setup needed — `main.rs` sets a default `EnvFilter` of `jana2u_pos_backend=info,tower_http=info,info` (overridable via `RUST_LOG`), and `app.rs`'s `TraceLayer` is explicitly configured with `DefaultMakeSpan`/`DefaultOnRequest`/`DefaultOnResponse` at `Level::INFO` — tower_http's own defaults for those three are `DEBUG`, which would stay silent under an `info`-level filter. If this layer is ever touched, keep it at `INFO` (or lower the filter instead) so request activity doesn't silently disappear.

**Feature modules** (`src/modules/<name>/`): `auth`, `billing`, `customers`, `inventory`, `print_jobs`, `purchases`, `repairs`, `reports`, `supplier_products`, `suppliers`, `users` — one per frontend feature (`suppliers`/`supplier_products`/`purchases` split into three modules because the frontend itself splits them into three feature folders — see **Suppliers, supplier-products & purchases** below; `auth`/`users` split the same way — see **Auth, users & permissions** below). Every module is layered the same way: `routes.rs` (HTTP only — extractors, `#[utoipa::path]`, `pub fn router() -> OpenApiRouter<AppState>`) → `service/` (business rules: validation, orchestration, translating a missing repository result into the right `AppError`) → `repository/` (Mongo only — no `AppError::not_found`, just `Option`/`Vec`/counts straight from the driver). `mod.rs` declares `repository`/`service` as **private** submodules (`mod repository; mod service;`) so nothing outside the module tree can reach past `routes` into persistence, exposing only `pub mod routes;` (plus `pub mod model;` for `inventory`, which also has Mongo document shapes to hold). Within a module, `repository`/`service` functions are `pub(crate)` and called via fully-qualified paths (e.g. `repository::product::find_product_by_id`) rather than a `pub(super) use *` re-export — repository functions are prefixed by the entity they act on (`find_product_by_id`, `find_category_by_name`, not bare `find`) specifically so sibling files like `product.rs` and `category.rs` can each have their own `insert`/`delete`-shaped operation without name collisions if ever flattened. `billing`, `customers`, `print_jobs`, `repairs`, `reports` currently only have a placeholder `GET /` status route, with empty `repository`/`service` stubs already scaffolded (see each `repository/mod.rs`/`service/mod.rs`) and awaiting real logic. `inventory` is built out as the reference example: `service`/`repository` are further split into `product.rs`/`stock.rs`/`category.rs`/`subcategory.rs` (full product CRUD — list/get/create/update/delete, batch delete, stock adjustment + movement history, low-stock — plus full category/subcategory management. Every route in this module except the `GET /` module-status stub requires a token: reads are gated by `CurrentUser::require_permission(INVENTORY_READ)`, product/stock writes by `INVENTORY_WRITE`, and create/rename/delete a category plus add/remove a subcategory stay behind `AdminUser` — see `core/middleware/auth.rs`) backed by a `categories` collection and a separate `subcategories` collection (both seeded via `cargo run --bin seed_providers`). **Cross-collection references always go through the referenced document's `key`, never its (renameable) name or its Mongo `_id`** — this is the general pattern for any module that owns reference data another record points to: a `ProductDocument` stores `category_key`/`subcategory_key` (immutable foreign keys, generated once and never client-supplied — see **Custom Prefixed Unique Model Keys** below), never a category/subcategory name string. This makes renaming a category (or subcategory) a pure display-label change — `service::category::update_category` never needs to cascade a rename onto `products`, since the FK it stores never changes. Deleting still guards against orphaning: `delete_category`/`remove_subcategory` block with a 409 (`CATEGORY_IN_USE`/`SUBCATEGORY_IN_USE`) while any product still references that `category_key`/`subcategory_key`; once the guard passes, `delete_category` also cascade-deletes every `SubcategoryDocument` under that category (safe because a product can only hold a `subcategory_key` whose subcategory has that same `category_key` — enforced by `service::product::ensure_valid_category` at write time). `CreateProductRequest`/`UpdateProductRequest` and the category/subcategory admin endpoints' path params are all key-based (`categoryKey`/`subcategoryKey` in JSON and URL path segments) — a client must resolve a display name to its key (e.g. via `GET /categories/valid`) before submitting a write; API *responses* additionally include the resolved display name alongside the key (e.g. `Product.category`/`.categoryKey`) so callers don't have to cross-reference `GET /categories` just to render a label. `model.rs` holds its Mongo document shapes (kept separate from `domain::inventory`'s API-facing types). See **API docs** below for the required pattern when adding routes, and use `inventory` as the template for building out another module's `service`/`repository` layers.

**SKU generation** (`modules/inventory/service/sku.rs` + `repository/sku_counter.rs`): a product's `sku` is never client-supplied — `CreateProductRequest` has no `sku` field. `service::product::create_product` validates `category_key`/`subcategory_key` (`service::product::ensure_valid_category`, which also resolves and returns the category/subcategory **names** for the keys) and generates the SKU from those resolved names by calling `service::sku::generate_sku(db, category_name, subcategory_name)`, which derives a 3-letter uppercase code per name (`service::sku::derive_code` — first 3 ASCII letters, padded with `X` if the name has fewer than 3) and appends an atomically-incremented, per-prefix sequence (e.g. `"Phone Repairs"` + `"Screens"` → `PHO-SCR-0001`, `PHO-SCR-0002`, ...). `generate_sku`/`derive_code` themselves are unaware of keys — they always operate on names, resolved by the caller first. The sequence lives in a dedicated `sku_counters` collection (`{ _id: "<prefix>", seq }`), incremented via `find_one_and_update` + `$inc` + `upsert(true)` — the standard Mongo auto-increment pattern, safe under concurrent creates without a uniqueness-retry loop. SKUs are generated once and are immutable thereafter (`update_product` never touches `sku`, even if `category_key`/`subcategory_key` changes) — apply the same "generate from a derived code + atomic counter, never let the client set it" approach to any other module that needs a human-readable, collision-free identifier.

**Suppliers, supplier-products & purchases** (`modules/suppliers`, `modules/supplier_products`, `modules/purchases`; domain types in `domain/suppliers.rs`/`domain/supplier_products.rs`/`domain/purchases.rs`): three separate modules, each mounted at its own top-level `/api/<name>` prefix (`/api/suppliers`, `/api/supplier-products`, `/api/purchases`), rather than one `suppliers` module with sub-paths — `supplier_products`/`purchases` are both queried by *either* `supplierKey` or `productKey` (a product's linked suppliers, a product's purchase history), so they're independent join/history resources, not sub-resources nested under one parent. Because each module's collection root is itself the real "list"/"create" endpoint (`GET/POST /`), none of the three has the placeholder `GET /` module-status route the other modules have — there's no unused path left for one. All three follow the same `routes.rs` → `service/` → `repository/` layering as `inventory`, with `model`/`repository` private (`suppliers::model` stays `pub` like `inventory::model`, for direct fixture seeding in tests; `supplier_products`/`purchases` don't need that, so their `model` stays private). Every route across all three — reads included — requires `AdminUser`, not just `CurrentUser`: supplier identity/pricing and purchase history are treated as business-sensitive, so even `GET /suppliers`/`GET /purchases` are behind `security(("bearerAuth" = []))` plus the `role == Role::Admin` check, not merely "any authenticated caller." (This is a deliberate departure from the read-permission/write-permission split `inventory` and `customers` use — see **Auth, users & permissions** below for why "admin" specifically, not a permission.)
  - **Cross-module access**: `supplier_products`/`purchases` both need to validate and enrich against `inventory`'s products and `suppliers`' suppliers, and `inventory::service::product::delete_product`/`delete_products` needs to cascade into `supplier_products`. Since a module's `repository` is always private (only `service` is `pub`), all of this goes through `pub(crate)` functions on the *other* module's `service`, never its `repository` — e.g. `inventory::service::product::get_product_by_key`/`get_products_by_keys` (the latter added specifically for `purchases::service::purchase::list_purchases`'s batch enrichment), `suppliers::service::get_supplier_by_key`/`get_suppliers_by_keys`, `supplier_products::service::link::delete_links_for_supplier`/`delete_links_for_product`. Apply this same "reach the other module through its `service`, add a `pub(crate)` fn there if the one you need doesn't exist yet" approach for any future cross-module dependency — never make a `repository` module `pub` to work around it. This is also why `list_purchases`' supplier/product batch enrichment stays as two `get_*_by_keys` calls plus an in-memory `HashMap` zip instead of a `$lookup` — see **MongoDB Aggregation Pipelines** below for where pipelines are and aren't the right tool.
  - **Referential integrity without fallbacks**: `supplierKey`/`productKey` (and `supplier`/`product` on a link or purchase) follow the same key-based-FK rule as `category_key`/`subcategory_key` (see **Custom Prefixed Unique Model Keys** below) — `upsert_link`/`replace_links_for_supplier`/`record_purchase` all validate both keys resolve to a real document *before* writing (404 if not), rather than trusting client input. Deleting a supplier is blocked with 409 `SUPPLIER_HAS_PURCHASES` while any purchase still references it (`suppliers::service::delete_supplier`, mirroring `CATEGORY_IN_USE`) — but only cascades a delete of its `supplier_products` links, since those are pure linking metadata, not audit history. Products stay unconditionally deletable (matching `delete_product`'s existing behavior); deleting one cascades its `supplier_products` links the same way. A `Purchase`'s embedded `supplier`/`product` enrichment is resolved live at read time and reuses the existing `resolve_display_names`-style graceful-degradation pattern — `Option<SupplierSummary>`/`Option<ProductSummary>`, omitted (never a fabricated placeholder) if the reference no longer resolves — rather than snapshotting denormalized data onto the purchase or soft-deleting the supplier/product.
  - **Stock intake**: `purchases::service::purchase::record_purchase` increments the referenced product's `stock_quantity` and writes a `StockMovementType::PurchaseReceipt` movement (`reference_id` = the purchase's `key`) by calling `inventory::service::stock::apply_stock_delta` — the same negative-stock-guarded, stock-plus-movement-in-one-write function `adjust_stock` (the `PATCH /products/{id}/stock` handler, tagged `ManualAdjustment`) is now a thin wrapper around. Any future module that needs to move stock (a sale, a repair consuming parts, a return) should call `apply_stock_delta` with its own `StockMovementType` rather than writing to `stock_quantity`/`stock_movements` directly.

**Auth, users & permissions** (`modules/auth`, `modules/users`; domain types in `domain/auth.rs`/`domain/users.rs`): split into two modules along the same "one module per frontend concern" line as `suppliers`/`supplier_products`/`purchases` — `users` owns the `users` collection, `UserDocument`, and all account CRUD/role management (admin-provisioned only; there is deliberately no public self-registration endpoint), while `auth` owns only its own `login_sessions` audit-log collection and exists to issue and describe JWTs (`POST /auth/login`, `GET /auth/me`, `GET /auth/sessions`). `auth` never touches the `users` collection directly — it reaches account data exclusively through `users::service::verify_credentials`/`get_user` (`pub`, not `pub(crate)`, specifically so `auth` — a sibling module — and `src/bin/seed_admin.rs` — a separate binary crate — can both reach it), the same "reach the other module through its `service`, never its `repository`" rule `supplier_products`/`purchases` already follow for `suppliers`/`inventory`. Three fixed roles (`domain::users::Role::{Admin,Manager,Staff}`) each map to a hardcoded default permission set (`core::constants::roles::default_permissions`) built from flat string constants in `core::constants::permissions` (`"module:action"`, e.g. `"users:manage"`, `"sessions:view"`) — adding a new permission for a future module is two edits: a new constant in `permissions.rs`, then slotting it into the relevant role's slice in `roles.rs`. `suppliers`/`supplier_products`/`purchases` deliberately have no corresponding permission constants — they're gated by `AdminUser` directly (see above), since only Admin may touch them at all; a permission would imply finer-grained delegation that doesn't exist there. `inventory` is the reference example of the permission pattern instead: `INVENTORY_READ` (held by all three roles) gates every read, `INVENTORY_WRITE` (Admin and Manager only) gates every product/stock mutation, so a Staff token can browse the catalog and its audit trail but never change either. Permissions are never persisted per-user (no per-account overrides) — they're derived fresh from `role` at every login and embedded in the JWT's `permissions` claim, so route-level checks never need a database round trip; a role change only takes effect on that user's next login, since there is no revocation/blacklist infra to force-refresh a live token.

**User-management hierarchy**: `modules/users`' own endpoints (`GET/POST /users`, `GET/PATCH/DELETE /users/{id}`) are gated by `CurrentUser::require_any_permission(&[USERS_MANAGE, USERS_MANAGE_STAFF])`, then further scoped in `service` by the caller's role via `manageable_roles(caller_role) -> &[Role]` (private to `modules::users::service`): an Admin (`USERS_MANAGE`) may create/view/edit/delete Manager and Staff accounts; a Manager (`USERS_MANAGE_STAFF`) may do the same to Staff accounts only; Staff has neither permission and can't reach these endpoints at all. Critically, **an Admin account is never manageable through this API by anyone — not even by another Admin** — `Role::Admin` never appears in any caller's `manageable_roles`, so `GET/PATCH/DELETE /users/{id}` against an Admin-role id 404s (`USER_NOT_FOUND`) exactly as if that id didn't exist, and `POST /users`/`PATCH /users/{id}` reject `role: "admin"` with 403 `PERMISSION_DENIED` for every caller, Admin included. This is a single-shop POS deployment that only ever has one Admin: `service::create_user` (the raw, unrestricted function `src/bin/seed_admin.rs` calls directly, bypassing the HTTP-reachable `create_user_for_caller` wrapper that enforces the scoping above) additionally refuses to insert a second `role: Admin` document at all (409 `ADMIN_ALREADY_EXISTS`), so even re-running `seed_admin` with a different email can't create a second one. One consequence of no role ever managing its own role: there is no dedicated "can't delete your own account" guard — it's unreachable by construction (an Admin can't target Admin, a Manager can't target Manager), so don't reintroduce one unless the hierarchy itself changes. `POST /api/auth/login` verifies email/password via `argon2` (`users::service::hash_password`/`verify_password`, Argon2id via the `password-hash` crate's `PasswordHasher`/`PasswordVerifier`) and, on success, returns a single access JWT (`jsonwebtoken`, HS256) — no refresh token, `JWT_EXPIRY_HOURS` (a required env var, in `core/config/env.rs`) controls how long it stays valid, and the client just re-authenticates via login once it expires. `GET /api/auth/me` re-reads the account from Mongo (rather than only decoding the token) specifically so a deactivated (`isActive: false`) account is caught on its next `/me` call even though its still-valid token can't otherwise be revoked. `core::middleware::auth::CurrentUser` additionally carries `permissions: Vec<String>` decoded straight from the JWT; `CurrentUser::require_permission(&self, permission: &str) -> AppResult<()>` (403 `PERMISSION_DENIED` if absent) is the pattern for gating a route by permission instead of by role — called as the first line of the handler body rather than via a new extractor type, since Axum's `FromRequestParts` can't take a runtime constructor argument without unstable const generics over `&'static str`; `AdminUser` (unchanged in shape, now compares against `Role::Admin` instead of the literal string `"admin"`) remains the pattern for "must literally be Admin" gates like `inventory`'s existing category/subcategory management — it is deliberately *not* migrated to `require_permission` here, since that would be a pure refactor with no behavior change. Every successful login is also recorded in `auth`'s own `login_sessions` collection (`modules::auth::model::LoginSessionDocument`, listed via the permission-gated `GET /api/auth/sessions`) — unlike every other cross-module reference in this codebase, its `name_at_login`/`email_at_login`/`role_at_login` fields are a **snapshot at the moment of login**, not a live join against the current account (contrast with `Purchase`'s live-resolved `supplier`/`product` enrichment): an audit trail should keep reading the way it did when the login happened even if the account is later renamed or its role changes. Bootstrap the first Admin account with `cargo run --bin seed_admin` (reads `SEED_ADMIN_EMAIL`/`SEED_ADMIN_PASSWORD`/`SEED_ADMIN_NAME`, create-if-missing — never resets an existing account's password on re-run) since admin-provisioned-only registration otherwise has no way to create the very first user.

**Route File Organization**: Every module's `routes.rs` MUST follow a clean, structured ordering using section banners (`// ============================================================================`) in this exact sequence:
1. `// Router`: `pub fn router() -> OpenApiRouter<AppState>` with `routes!(...)` calls grouped and commented by feature to mirror the file layout.
2. `// Helpers`: Private helper functions for that module (e.g. `parse_object_id`, whitelist mapping, numeric validation).
3. `// <Feature Sections>`: Grouped feature handler blocks (e.g., `// Module status`, `// Products`, `// Stock`, `// Categories`, `// Subcategories`). Read/validation endpoints (such as `/categories/valid`) belong inside their primary domain section next to other reads rather than at the bottom of the file.

**Custom Prefixed Unique Model Keys**: Every MongoDB collection document model MUST include a custom unique `key: String` alongside `_id: ObjectId`. Keys follow the format `<prefix>_<nanoid>` (e.g. `prod_x7K9mP2...` for products, `cat_B8nL1q...` for categories, `subcat_...` for subcategories, `sm_9pX2kQ...` for stock movements, `ak_...` for API keys, `sup_...` for suppliers, `splink_...` for supplier-product links, `pur_...` for purchases, `usr_...` for users, `lgs_...` for login sessions). Generated via `crate::core::id::generate_id(prefix)` (defined in `core/id.rs`, backed by `nanoid!(16)`). From now onwards, all models, seed scripts, and API domain response payloads MUST include and maintain this `key` field, **and any field on one model that references another collection's document MUST store that document's `key`** — never its display name and never its raw `_id`/`ObjectId` (see `ProductDocument.category_key`/`.subcategory_key` in `modules/inventory/model.rs` for the reference example). The one deliberate exception is a pure internal sequence/counter table like `sku_counters` (`modules/inventory/repository/sku_counter.rs`) — it's not a business entity, so it has no `key`; its `_id` (the derived SKU prefix) already *is* the meaningful key.

**Collection Document Timestamps (`created_at` & `updated_at`)**: Every MongoDB collection document model (and its API domain representation) MUST include `created_at` and `updated_at` timestamps (`BsonDateTime` in models, `DateTime<Utc>` in domain structs). When creating documents, set both `created_at` and `updated_at` to the current timestamp (`BsonDateTime::now()`); when updating documents or sub-resources, update `updated_at`. Models must include `#[serde(default = "BsonDateTime::now")]` for deserialization backward compatibility with existing stored documents.

**`core/`** — cross-cutting infrastructure, not domain logic:
- `core/config/env.rs` — `Config::from_env()` parses all required env vars once at startup and fails fast (`MONGODB_URI`, `MONGODB_DB_NAME`, `JWT_SECRET`, `JWT_EXPIRY_HOURS` required — see **Auth, users & permissions** above; `PORT` is the one optional var, defaulting to 8080).
- `core/middleware/auth.rs` — `CurrentUser` is an Axum extractor (`FromRequestParts<AppState>`) that verifies the `Authorization: Bearer <jwt>` header with `jsonwebtoken` using `Config::jwt_secret`, decoding a `role: Option<domain::users::Role>` and a `permissions: Vec<String>` claim. Add `CurrentUser` as a handler argument to require auth on a route; omit it to keep a route public. **Auth is opt-in per handler and nothing flags one that forgets it** — a handler declaring neither extractor is silently public, and it still compiles, still passes every other test, and is still documented accurately by the OpenAPI derive. That is exactly how `inventory`'s product/stock routes served the whole catalog — and accepted creates, price edits, stock adjustments and bulk deletes — with no token at all. The complete intentional-public list is `GET /api/health`, `POST /api/auth/login`, Swagger (`/docs`, `/api-docs/openapi.json`) and the five `GET /api/<module>` status stubs (`inventory`, `billing`, `repairs`, `reports`, `print-jobs`); it is restated in a comment in `app::build_router` and enforced route-by-route by `tests/authorization_test.rs`. Anything else must take an extractor. Call `CurrentUser::require_permission("some:permission")` as the first line of a handler body to further gate it by permission (403 `PERMISSION_DENIED` otherwise). `AdminUser` wraps `CurrentUser` and additionally requires `role == Some(Role::Admin)` (403 `ADMIN_REQUIRED` otherwise) — the pattern for "must literally be Admin" endpoints like inventory's category management; add `AdminUser` as a handler argument the same way, and mark the route `security(("bearerAuth" = []))` in its `#[utoipa::path]`. There is deliberately no tenant/org-membership middleware yet — this is a single-shop deployment for now. Note `jsonwebtoken` needs its `rust_crypto` feature enabled in `Cargo.toml` (see comment there) — without it, `encode`/`decode` panic at runtime with no crypto backend installed.
- `core/error.rs` — `AppError` (`NotFound`, `Validation`, `Unauthorized`, `Forbidden`, `Internal` — each `{ message, code: Option<String> }` — plus `Custom { status, code, message }` for anything else) implements `IntoResponse`, serializing to `core::response::ErrorResponse` (`{ success: false, message, code, statusCode }`, camelCase) with the matching HTTP status; also `From<mongodb::error::Error>` / `From<jsonwebtoken::errors::Error>`, so handlers can `?`-propagate Mongo/JWT failures directly. Use `AppResult<T>` as the handler return type. Construct via `AppError::not_found("msg")` / `AppError::not_found_with_code("msg", "SOME_CODE")` (same pattern for `validation`/`unauthorized`/`forbidden`/`internal`), or `AppError::custom(status, "CODE", "msg")` for anything outside those five. A missing `code` on the non-`Custom` variants defaults to the upper-snake-case of the variant name (e.g. `NOT_FOUND`).
- `core/response.rs` — `ApiResponse<T>` is the success envelope every handler should return: `{ success: true, data: Option<T>, message: Option<String> }` (both fields omitted from JSON when `None`), built via `ApiResponse::success(data, message)` / `::data(data)` / `::message(message)`. Its `IntoResponse` impl **always returns HTTP 200** — a handler returning `Json<ApiResponse<T>>` directly (as opposed to `AppResult<Json<ApiResponse<T>>>` returning `Err(AppError::...)`) cannot produce a non-2xx status; failure cases must go through `AppError`, not `ApiResponse`. Also defines `ErrorResponse`, the JSON shape `AppError::into_response` produces (see above) — don't construct `ErrorResponse` directly outside `core/error.rs`.
- `core/constants/` — central source of truth for constants across the backend: `modules.rs` (feature module names), `codes.rs` (standardized error and status codes), `http_status.rs` (re-exported HTTP status codes), `prefixes.rs` (model key prefix constants like `PRODUCT`, `CATEGORY`, `SUBCATEGORY`, `STOCK_MOVEMENT`, `API_KEY`, `SUPPLIER`, `SUPPLIER_PRODUCT`, `PURCHASE`, `USER`, `LOGIN_SESSION`), `permissions.rs` (flat `"module:action"` permission strings), and `roles.rs` (`default_permissions(Role) -> &[&str]`, the hardcoded role→permission-set table — see **Auth, users & permissions** above).
- `core/utils.rs` — reusable cross-cutting helpers for route handlers (`module_status_response`, `parse_object_id`, `regex_escape`, `build_bson_regex`, `calculate_pagination`).
- `core/openapi.rs` — `ApiDoc` (`#[derive(utoipa::OpenApi)]`) holds only top-level metadata (title/description/version, tags, the `bearerAuth` security scheme); actual paths are collected from the modules at router-build time, not listed here.

**`domain/`** — pure business types shared across modules (no I/O, no Axum/Mongo types beyond `serde`/`utoipa` derives). Currently holds `HealthResponse`/`ModuleStatusResponse`, the inner `data` payloads that route handlers wrap in `core::response::ApiResponse<T>` before returning (e.g. `Json<ApiResponse<ModuleStatusResponse>>`, not the raw type) — populate further as modules grow instead of putting business logic directly in `routes.rs`.

**`clients/mongo.rs`** — `connect(uri, db_name)` builds the `mongodb::Client`, pings the target database, and returns a `Database` handle. This is the only place Mongo connection setup happens; modules access `AppState.db` rather than reconnecting. `ClientOptions::parse` is explicitly given `ResolverConfig::cloudflare()` rather than the OS default — on some hosts (observed on macOS with a link-local IPv6 nameserver like `fe80::...%en0`) the driver's built-in resolver fails to parse the system DNS config, which breaks `mongodb+srv://` SRV/TXT lookups with a `DnsResolve` error even though the URI and credentials are correct. Any other place a `ClientOptions` gets built directly from a URI (e.g. `tests/openapi_test.rs`) needs the same `.resolver_config(ResolverConfig::cloudflare())` call for the same reason.

**`workers/`** — placeholder for background jobs (e.g. scheduled reports, print queue processing); empty so far.

**`src/bin/`** — standalone binaries sharing the lib's config/Mongo plumbing, run via `cargo run --bin <name>`, not part of the HTTP server.

## MongoDB Aggregation Pipelines

Use an aggregation pipeline wherever the driver supports one and it collapses multiple round trips
(or an unsafe read-modify-write) into one — but a pipeline is a read/transform tool, not a
universal replacement for CRUD. Apply it by operation type:

- **Reads** — any `find`/`find_one` with a non-trivial shape (joins, grouping, counts, pagination
  computed server-side) should become `aggregate([...])`. A single `$match` stage can express any
  plain filter, so there's no reads-only case a pipeline can't cover.
- **Updates** — MongoDB 4.2+ accepts an *array of aggregation stages* in place of an
  update-operator document for `updateOne`/`find_one_and_update`, letting the new value be
  computed from the document's current fields server-side in one atomic round trip. Use this
  whenever a plain `$set` isn't enough because the new value depends on the old one (an increment,
  a computed field) — see `repository::product::adjust_product_stock_pipeline`
  (`modules/inventory/repository/product.rs`): `find_one_and_update` with a pipeline `$set`
  computing `{ "$add": ["$stock_quantity", delta] }`, with the negative-stock guard folded
  straight into the query filter (`"stock_quantity": { "$gte": -delta }` when `delta < 0`) so the
  check and the write are one atomic operation instead of a read-then-write race.
- **Inserts and deletes** — stay as plain `insert_one`/`insert_many`/`delete_one`/`delete_many`
  regardless; there is no aggregation-pipeline form of either, so there's nothing to gain.

Within those rules, only reach for a pipeline where it's a *real* win:

- **Do** collapse a "fetch collection A, fetch collection B, group/zip in Rust with a `HashMap`"
  pattern into a single `$lookup`-based aggregate **when both collections belong to the same
  module** — e.g. `repository::product::list_products_with_display_names` (`$lookup` joining
  `products` → `categories`/`subcategories`) and
  `repository::category::list_categories_with_subcategories` (`$lookup` joining `categories` →
  `subcategories`), both in `modules/inventory/repository/`. Also reach for `$facet` when one
  endpoint needs several independent aggregates (counts, grouped-and-paginated sub-results) in one
  round trip instead of issuing them as separate queries — see
  `repository::product::aggregate_overview`, which computes the Inventory & Stock overview page's
  dashboard metrics, per-category counts, and per-subcategory paginated product pages in a single
  `$facet` pipeline (replacing what used to be a query issued once per subcategory in a loop).
- **Don't** wrap a trivial single-document `find_one` (`find_product_by_id`,
  `find_supplier_by_key`, `find_category_by_name`, etc.) in `aggregate([{ "$match": ... }])` —
  that's pipeline ceremony for something `find_one` already does in one line.
- **Don't** use `$lookup` across a module boundary. `purchases::service::purchase::list_purchases`
  and `supplier_products::service::link`'s batch enrichment against `suppliers`/`inventory` stay
  as separate `get_*_by_keys` calls into the other module's `service` plus an in-memory `HashMap`
  zip (see **Cross-module access** above) — a `$lookup` there would mean one module's `repository`
  reaching directly into another module's collection, which breaks the "reach another module
  through its `service`, never its `repository`" rule this codebase enforces everywhere. That
  boundary is what lets e.g. `inventory::service::product::get_product_by_key` apply its own
  not-found/validation logic consistently to every caller — `$lookup` would bypass it.

## API docs (OpenAPI/Swagger)

Swagger UI: `http://localhost:8080/docs`. Raw OpenAPI 3.1 JSON: `http://localhost:8080/api-docs/openapi.json`. Generated via `utoipa` + `utoipa-axum` + `utoipa-swagger-ui` — there is no hand-written spec file to fall out of sync.

**The docs are only correct if every route follows this pattern** (see any `modules/*/routes.rs` for a working example):
1. Annotate the handler with `#[utoipa::path(get, path = "/foo", tag = "<module>", responses((status = 200, body = ApiResponse<SomeResponseType>)))]` (also add `request_body = ...` / path or query params as needed, and `security(("bearerAuth" = []))` if the route requires `CurrentUser`). Success responses are wrapped in `core::response::ApiResponse<T>`, not the bare domain type — see `core/response.rs` above.
2. Response/request payload types (the `T` inside `ApiResponse<T>`, and any request body type) need `#[derive(utoipa::ToSchema)]` alongside `serde::Serialize`/`Deserialize`.
3. Register the handler in that module's `router()` via `OpenApiRouter::new().routes(routes!(handler_one, handler_two, ...))` — **never** mount a handler with plain `axum::routing::get/post/...` inside a module's `router()`, since only handlers passed through the `routes!()` macro get collected into the OpenAPI document.

`tests/openapi_test.rs` asserts `/api-docs/openapi.json` contains a path for every module and that `/docs/` serves — run it after adding a module or route to catch a handler that was wired with plain `axum::routing` instead of `routes!()`.

**Postman collection** (`postman/backend.postman_collection.json`, environments in `postman/Developement.postman_environment.json`/`Production.postman_environment.json`): a hand-maintained companion to the OpenAPI spec above — nothing generates it, so **any time a route is added, removed, or has its path/method/params/body shape changed, update this file in the same change**. Mirror the existing conventions: one folder per module (matching `core::constants::modules`), sub-folders per `routes.rs` section banner (e.g. Inventory's `Module`/`Overview`/`Products`/`Stock`/`Categories`/`Subcategories`, in the same order as `routes.rs`), one request per handler named after what it does (not the HTTP method). Query params go in the URL's `query` array with a `description` explaining what each one filters/sorts and `"disabled": true` for every optional one (so the raw URL stays a realistic fully-populated example while the actual request only sends what's enabled) — required params like `page`/`limit` stay enabled. Request bodies are `raw`/`json` with realistic example values, never empty placeholders. Reuse an existing collection variable (`{{categoryKey}}`, `{{productKey}}`, `{{supplierKey}}`, etc. — see the collection's top-level `variable` array) instead of inventing a new one for the same concept. Every request inherits the collection-level Bearer auth; only note per-request auth requirements in its `description` when they differ from the norm (e.g. admin-gated or permission-gated routes — see the collection `info.description` for the general rule). Edit the file directly as JSON (it round-trips losslessly through `json.load`/`json.dumps(..., indent=2, ensure_ascii=True)` in Python, which is the safest way to make a small addition without reformatting the whole file) rather than requiring Postman itself to make small updates.

## Code Comments

Every file should make it obvious what it does and why without the reader having to reverse-engineer intent from the code alone. Apply this whenever you touch a file, not just when writing something new:

1. **Module-level banner**: every file — even a 3-line re-export `mod.rs` — opens with a plain `//` comment (not `//!`) stating what it owns and, where relevant, what it deliberately does *not* do. See `domain/inventory.rs` ("no I/O, no Mongo/Axum types...") or `modules/inventory/repository/mod.rs`.
2. **Doc comments (`///`) on `pub`/`pub(crate)` items** whose purpose isn't obvious from the signature alone: every `repository::*` function gets a one-liner naming the query intent, every `service::*` function gets a one-liner naming the business rule it enforces, every `domain`/`model` struct or enum gets a one-liner on non-obvious fields (why a field exists, why it's `Option`, why an enum has the variants it has). Trivial CRUD wrappers still get a short one-liner for consistency — not a paragraph.
3. **Inline comments explain *why*, not *what***: a non-obvious invariant, a workaround, or a decision a future reader would otherwise have to reverse-engineer (e.g. the `$expr`/`$lte` low-stock query shape in `modules/inventory/repository/product.rs`, the cascade-delete-of-subcategories-on-category-delete safety argument in `modules/inventory/service/category.rs`, the DNS resolver workaround in `clients/mongo.rs`). Never restate what a line of code already says — if removing the comment wouldn't confuse a future reader, don't write it.
4. **Reference examples**: `clients/mongo.rs` (DNS resolver workaround), `core/middleware/auth.rs` (why `CurrentUser`/`AdminUser` exist and how they gate routes), `modules/inventory/service/category.rs` (key-based-reference/cascade-delete rationale), `modules/inventory/model.rs` (`CategoryDocument`'s DB-backed-source-of-truth rationale and the `ProductDocument`/`SubcategoryDocument` key-FK pattern), `core/error.rs` (`AppError`'s variant/`Custom`-escape-hatch design).
